# steamac — официальный ARM64 SteamOS (образ Steam Frame) в ВМ на Apple Silicon

[English](README.md) · **Русский** · [简体中文](README.zh.md)

На macOS 15 (Sequoia) настоящий SteamOS от Valve для Steam Frame запускается в лёгкой ВМ на
Hypervisor.framework (libkrun) с GPU-ускорением через Venus.

```
игра (DX9/10/11) ─ DXVK (Proton 11, x86 через FEX) ─ Vulkan
   └─ гостевой Mesa Venus ─ virtio-gpu (blob, 16K-выравнивание)
        └─ libkrun ─ virglrenderer (Venus) ─ MoltenVK | KosmicKrisp ─ Metal
```

Vulkan на Metal — по умолчанию MoltenVK из форка UTM (геометрические шейдеры, robustness2) +
`VK_EXT_depth_clip_enable` (PR #2712) + наши исправления. KosmicKrisp (Vulkan-драйвер Mesa на
Metal 4) — экспериментальная альтернатива на macOS 26+ (см. «Vulkan-драйвер»).

## Требования

- Mac на Apple Silicon, macOS 15+, ~150 ГБ свободного места (образ диска разреженный).
- Xcode 26+ (полный: его `actool` собирает иконку приложения из Icon Composer-документа), Homebrew, rustup.
- KosmicKrisp (необязательно, альтернативный Vulkan-драйвер): собирается только на macOS 26+;
  `host/kosmickrisp/build.sh` сам ставит Homebrew-зависимости (`llvm spirv-llvm-translator spirv-tools vulkan-loader glslang`).
- OrbStack (или Docker с arm64 и `--privileged`): ядро, Mesa и образ диска собираются в Linux-контейнерах.
- Homebrew-пакеты: `meson ninja pkg-config dtc xz lld sshpass go` (`go`: лицензии вложенных gvproxy/desync).
- libepoxy 1.5.10 собирается из закреплённых исходников через `host/libepoxy/build.sh` перед
  virglrenderer и libkrun; все три используют `MACOSX_DEPLOYMENT_TARGET=15.0`, в том числе на
  macOS 26/27. Сборка бандла отклоняет Mach-O с deployment target выше macOS 15.0
  (только KosmicKrisp может требовать 26.0).

## Сборка и запуск

```sh
./build.sh          # стек Vulkan: MoltenVK, virglrenderer, libkrun, лаунчер, ядро, Mesa, диск
./build.sh dxmt     # DXMT + исполнитель wmtr и гостевые библиотеки; затем пересобрать слой и лаунчер (ниже)
./run.sh            # окно с SteamOS
```

Части по отдельности: `./build.sh host`, `./build.sh guest`, либо скрипты из таблицы ниже.
Образ SteamOS скачивается с серверов Valve (подписанный RAUC-бандл), подпись и sha256 проверяются.

Рядом с гостевыми артефактами релиза лежат `.inputs.json`: записи успешной сборки связывают хеши
выбранных файлов рабочего дерева Git с байтами результата. Изменения этих исходников инвалидируют
запись; посторонние коммиты — нет. `host/launcher/bundle.sh` отказывает при отсутствующей или устаревшей
записи до изменения приложения; `dist.sh` также проверяет записи и ресурсы внутри уже собранного
приложения перед упаковкой. Ошибка указывает, какой шаг повторить. Чтобы обновить гостевые артефакты
без изменения существующего диска SteamOS: `guest/kernel/build.sh` (если его входы изменились или
записи нет), `scripts/build-image.sh builder rootfs`, `guest/mesa/build.sh`, затем
`scripts/build-image.sh initramfs layer` и наконец `host/launcher/build.sh`. Для старого артефакта без
записи нужна обычная сборка один раз; ядро переиспользует том сборки без `clean`.
Слои `ALLOW_NO_VENUS=1` предназначены только для тестов и не допускаются в релиз.

Параметры ВМ: `./run.sh --display 1920x1080 --cpus 10 --mem 24576` (полный список —
`work/out/steamac-vm --help`).

Плавность кадров: `./run.sh --perf-stats` (или `STEAMAC_PERF_STATS=1`) каждые 5 с пишет в терминал
интервалы кадров гостя и кадров на экране (p50/p95/p99/max, число интервалов > 25 и > 50 мс).
Подтормаживания при первом появлении нового эффекта — это компиляция шейдеров Metal (~50–100 мс на
пайплайн); результат кешируется Metal на диске, повторно эффект не тормозит, в том числе после
перезапуска игры или ВМ (замер через Venus: 102 мс → 0,95 мс на пайплайн в новом процессе).

Shader Pre-Caching Steam и «Allow background processing of Vulkan shaders» (Settings → Downloads) в ВМ
по умолчанию включены. Именно Pre-Caching приносит Proton транскодированные видео роликов: Steam
скачивает их для каждой игры (`steamapps/shadercache/<appid>/transcoded_video.foz`, например 836 МБ
для Heroes of Might and Magic: Olden Era, 3,8 ГБ для Diplomacy is Not an Option) и передаёт Proton
`STEAM_COMPAT_TRANSCODED_MEDIA_PATH`, а Proton проигрывает их вместо видео, которые не декодирует сам;
с выключенным Pre-Caching такие ролики показываются заглушкой. Собственный кеш DXVK (DXVK 2.7) лежит
в Wine-префиксе игры и работает в любом случае. Цена: каждый пайплайн, который обрабатывает
fossilize_replay Steam, компилирует Metal на Mac (~70–100 мс), а Steam обрабатывает заново после
своих обновлений шейдеров для игры и, для всех игр, после обновления лаунчера, меняющего MoltenVK
(идентичность драйвера Venus — хеш `pipelineCacheUUID` MoltenVK). Фоновая обработка делает большую
часть этого, пока Steam простаивает; остаток виден как «Processing Vulkan shaders» при запуске игры,
его можно пропустить кнопкой **Skip**. Выключить: Steam → Settings → Downloads → Enable Shader
Pre-caching (и/или Allow background processing of Vulkan shaders).

Штатный Steam держит фоновую обработку выключенной (отсутствующий в
`~/.local/share/Steam/config/config.vdf` `EnableShaderBackgroundProcessing` читается как 0). Перед
стартом Steam `/usr/lib/steamac/steam-shader-defaults` (ExecStartPre `steam.service`) пишет в блок
`ShaderCacheManager` `"EnableShaderBackgroundProcessing" "1"`, если значения там ещё нет, — один раз
на установку Steam (метка `config/steamac-shader-defaults`), поэтому выбор в настройках Steam
сохраняется. Лаунчер 1.4 выключал обе настройки (`"DisableShaderCache" "1"`,
`"EnableShaderBackgroundProcessing" "0"`); при первом старте Steam после обновления скрипт один раз
включает обе обратно, но только если там всё ещё ровно эти значения.

Заставка Steam при бездействии (Settings → Display → Screensaver в игровом режиме) в ВМ выключена.
Через несколько минут без ввода Steam ставит своё окно `Screensaver_uid<n>` поверх запущенной игры,
gamescope переводит на него фокус, и следующие клики попадают в Steam, пока не нажать Escape. Мышь,
планшет и клавиатура лаунчера сбрасывают таймер Steam, но игра, оставленная на долгом экране
загрузки или запущенная в VR (ввод шлема до Steam не доходит), для Steam простаивает; у macOS свои
заставка и сон дисплея. Перед стартом Steam `/usr/lib/steamac/steam-idle-screensaver` (ExecStartPre
`steam.service`) пишет `"IdleScreensaverACSeconds" "0"` и `"IdleScreensaverBatterySeconds" "0"`
(`InstallConfigStore/Software/Valve/Steam/System` в `config.vdf`; 0 = никогда), если их там нет, —
один раз на установку Steam (метка `config/steamac-idle-screensaver`), поэтому время заставки,
выбранное потом в настройках Steam, сохраняется.

Окружение, которое игре нужно от драйвера, — значение по умолчанию, а не код:
`/usr/lib/steamac/steam-title-defaults` (тоже ExecStartPre `steam.service`) ставит нужные слова
`VAR=value` перед параметрами запуска игры в Steam (`%command%`). Пока запись одна: Dragon's Dogma 2
(2054970) требует D3D feature level 12_1, который vkd3d-proton выводит из ROV и conservative
rasterization, — в Metal нет ни того, ни другого (у conservative rasterization нет API в Metal; ROV
потребовали бы raster order groups Metal под `VK_EXT_fragment_shader_interlock`), а игра проверяет
только уровень, поэтому он сообщается как `VKD3D_FEATURE_LEVEL=12_1 VKD3D_SHADER_MODEL=6_6`, вместе
с `VKD3D_DISABLE_EXTENSIONS=` (пусто). 64-битные атомики KosmicKrisp — только беззнаковые min/max,
поэтому `steam.service` по умолчанию скрывает `VK_KHR_shader_atomic_int64` и
`VK_EXT_shader_image_atomic_int64` от всех D3D12-игр (`Environment=VKD3D_DISABLE_EXTENSIONS=…` в его
drop-in; игра с другим 64-битным атомиком в шейдерах молча теряла бы эти пайплайны, а vkd3d-proton
по ним сообщает shader model 6.6), а подходящая игра возвращает их своими параметрами запуска.
Значение по умолчанию — унаследованное окружение Steam, а не строка в `gfx.txt`:
`steam-launch-wrapper` выставляет все переменные из `$XDG_RUNTIME_DIR/steam/env/gfx.txt`, затем из
`~/.config/steam/env/gfx.txt` поверх окружения игры, включая параметры запуска, так что
`VKD3D_DISABLE_EXTENSIONS`, записанная там, действует для всех игр. Запись применяется, только если
устройство Venus объявляет нужные ей возможности (у DD2 — 64-битные атомики, Apple8/M2 и новее), и
снимается с возвратом прежних параметров запуска, если при следующем старте Steam их уже нет
(драйвер переключён на MoltenVK, диск перенесён на M1); неудачная проверка ничего не меняет.
Существующее значение только дополняется спереди, а не заменяется, значение без `%command%` не
трогается, а правка в Steam после нашей побеждает (метка `~/.config/steamac/title-defaults.json`,
там же прежнее значение).
Слова `env` из профиля заменяют встроенную запись; без такого переопределения DD2 сохраняет значение по умолчанию с проверкой возможностей Venus.

SteamOS берёт часовой пояс и 12/24-часовой формат Mac (Настройки > Основные
**Использовать часовой пояс и формат времени Mac**, по умолчанию вкл., применяется при следующем запуске).
При каждой загрузке лаунчер добавляет `steamac.tz=<IANA-пояс Mac>` (`TimeZone.current`) и
`steamac.clock24=0|1` (локализованный шаблон часа `j`, учитывающий переключатель macOS **24-hour time**).
Initramfs направляет `/etc/localtime` на этот пояс (`timedatectl`, настройка Time zone в Steam
через `steamos-set-timezone` и часы Steam). `/etc/steamac/mac-timezone` помнит последний применённый
пояс; другой пояс, выбранный в SteamOS, сохраняется (пока снова не совпадёт с поясом Mac).
Перед запуском Steam `/usr/lib/steamac/mac-clock-format` записывает `b24HourClock` в файл аккаунта
`userdata/<account>/config/localconfig.vdf`, в
`UserLocalConfigStore/Software/Valve/Steam/FriendsUI/FriendsUIJSON`. Это переключатель
Settings → Time and date → 24-hour clock, а не общая настройка клиента: на новом диске до входа
файла нет, поэтому формат применяется при первом запуске Steam **после входа в аккаунт**.
В Desktop Mode задаётся `[Formats] LC_TIME` в `~/.config/plasma-localerc` (`en_GB.UTF-8` для
24-часового, `en_US.UTF-8` для 12-часового формата; это также выбирает локаль времени/даты).
Последние применённые значения и независимый выбор пользователя сохраняются в
`~/.config/steamac/mac-clock24.json`: изменение формата в Steam или Plasma останавливает
синхронизацию этой настройки с Mac, не затрагивая другую. С выключенной настройкой лаунчера
пояс и формат не трогаются. Для проверки можно передать
`--cmdline "console=hvc0 rootwait steamac.clock24=0"` (или `1`), не меняя настройки macOS.

Прогресс загрузки и выключения не пропадает до `ready`: первый клик или клавиша в окне сворачивает
полноэкранный оверлей в плашку внизу по центру (этап, процент, полоска, строка деталей вроде
`378 / 564 MB · 1.9 MB/s`; ввод проходит в гостя). Клик по плашке или Вид → Показать ход загрузки
разворачивает его обратно; с выключенным оверлеем (Настройки > Основные) сразу показывается плашка.
Пока идёт подготовка нового диска или загрузка / установка клиента Steam, клик и клавиши оверлей не
сворачивают, а свёрнутый кликом раньше оверлей разворачивается сам (`overlay: expanded for
steam-download`); свёрнутый через Вид → Показать ход загрузки остаётся плашкой до `ready`.
Заголовок окна до `ready` повторяет этап: «FX Steam Launcher — Загрузка обновления Steam 70%»,
«— Запуск Steam…», «— Выключение…». В лог: `overlay: collapsed to pill (click)` /
`expanded from pill`. После `ready`, если в окне ≥ 3 с нет картинки (scanout выключен или после его
установки/смены размера не пришло ни одного кадра) или показанный кадр ≥ 5 с чёрный (разреженная
выборка 64 × 40 точек, яркость < 8/255 у ≥ 99,5 %, не чаще 4 раз в секунду, ~3 мкс), а фокус не в
игре и гость не спит / не на паузе / не приостановлен, плашка пишет «Ожидание изображения от SteamOS…»
с причиной, heartbeat агента и CPU ВМ; исчезает с первым нечёрным кадром (`no-picture: shown after
5.0 s (black picture …)` / `hidden after … (first non-black frame)`). Проверка:
`work/out/steamac-vm --selftest-pill --selftest-out DIR`.

Пока в фокусе игра (`focus game <appid>`), если гость 2 с не присылает GPU-команд (virtio-gpu
control queue и Venus-кольца — счётчики `krun_gpu_get_activity`), поверх последнего кадра появляется
карточка «Работа продолжается — загрузка или компиляция шейдеров…» с загрузкой CPU ВМ; если вдобавок агент
гостя перестал присылать heartbeat (> 5 с) — «SteamOS не отвечает…» (это — при любом фокусе).
Простаивающий интерфейс Steam GPU-команд не шлёт минутами и индикатор не вызывает. Исчезает с первой
же GPU-командой или при уходе фокуса из игры; каждый случай пишется в лог (`stall: gpu idle 3.1 s
(guest alive, …)`). С `--perf-stats` раз в 5 с добавляется строка `perf: gpu ctrl/s=… ring/s=…
longest-idle=…`. Выключается в «Настройки > Основные». Агент живёт в каждой сессии gamescope (игровой
режим и режим рабочего стола): когда сессия заканчивается (Switch to Desktop, Return to Gaming Mode),
heartbeat не ждётся, пока агент новой сессии его не пришлёт; пока ВМ приостановлена или спит,
индикатор выключен, а после возобновления, пробуждения гостя и сна Mac отсчёт простоя и heartbeat
начинается заново.

| Клавиши в окне | |
|---|---|
| Ctrl+Cmd+F | полный экран (macOS включает Game Mode: Info.plist объявляет игру — `LSApplicationCategoryType` `public.app-category.games`, `GCSupportsGameMode`, `LSSupportsGameMode`; `gamepolicyd` пишет «Game mode status is now on») |
| Ctrl+Cmd+G | захватить / отпустить мышь вручную |
| Ctrl+Cmd+P | Панель производительности Metal Apple (FPS, интервал кадров, время GPU, память) вкл/выкл; то же Вид → Показать панель производительности Metal (Ctrl+Cmd+P) и Настройки > Экран. Библиотека панели загружается, только если панель включена при запуске ВМ: включение действует после перезапуска, выключение сразу скрывает панель, а выгружается она при следующем перезапуске. Панель Apple роняла ВМ с KosmicKrisp (Metal 4) на macOS 26, даже когда оверлей был скрыт (STEAMAC-59/7K/7Q/9X/9Y), поэтому её включение с KosmicKrisp требует подтверждения; альтернатива без панели Apple — Настройки > Основные > Записывать статистику равномерности кадров в журнал: записывается время вывода кадров гостя (не FPS игры). Отчёты о сбоях содержат запрошенное и фактическое состояние панели, признак внедрения её библиотеки и драйвер |
| Ctrl+Option | отпустить захваченную мышь |
| закрыть окно | выключение гостя (кнопка питания) |

Мышь (`--mouse auto`, по умолчанию): курсор SteamOS точно следует за курсором Mac, а курсор Mac над
картинкой скрыт, чтобы был виден только курсор gamescope (он появляется над чёрными полями,
кликабельной плашкой прогресса и ссылкой «Report…», меню и другими окнами, во время загрузки, на паузе и
во сне, и вне окна). gamescope
(игровой режим) не принимает абсолютные координаты, поэтому лаунчер ведёт его относительными
сдвигами без ускорения, в пикселях поверхности, которую показывает gamescope: агент сообщает её
размер в каждой строке фокуса (`focus steam 1920x1200`, когда в Steam Настройки > Дисплей >
Разрешение выбрано не родное: интерфейс меньше дисплея и растянут), а лаунчер отображает окно на эту
поверхность так, как gamescope вписывает её в дисплей (`--selftest-pointer`). Когда в госте в
фокусе игра (агент шлёт `focus game <appid> <w>x<h>`), первый
щелчок захватывает мышь (относительное движение для обзора мышью), Ctrl+Option отпускает; при
возврате в Steam захват снимается сам. Меню **Мышь**:
- **Захватывать мышь в этой игре** — авто-захват для текущей игры (сохраняется по appid);
- **Автоматически захватывать мышь в играх** — значение по умолчанию для всех игр;
- **Захватить / освободить мышь сейчас (Ctrl+Cmd+G)** — то же, что Ctrl+Cmd+G.

Эти и все остальные настройки — в окне **Настройки** (см. ниже), домен `es.fxgam.steamac`
(`defaults read es.fxgam.steamac`); при первом запуске они один раз копируются из прежнего домена
`dev.steamac.vm`. Metal хранит кеш шейдеров по идентификатору приложения, поэтому после смены
идентификатора первый запуск игр снова компилирует шейдеры (один «холодный» запуск).
`--auto-capture on|off` переопределяет значение по умолчанию на один запуск.
`--mouse tablet` — абсолютный планшет (gamescope его не принимает, так что только для других
композиторов в госте), `--mouse capture` — всегда захват по щелчку.

Доступ в гостя: `ssh -p 2222 steamos@127.0.0.1`, пароль `steamos` (меняется через
`STEAMOS_PASSWORD=... scripts/build-image.sh disk`). Консоль hvc0 — в терминале, где запущен `run.sh`.

SSH включается и выключается одним переключателем: **Настройки → Дополнительно → Включить SSH** (или
`--ssh-port N` / `--no-ssh`). Лаунчер на каждой загрузке передаёт `steamac.ssh=0|1`: при 0 порт на
Mac не открывается вовсе (gvproxy без проброса), а initramfs маскирует sshd в SteamOS. По умолчанию
SSH включён у dev-лаунчера (`work/out/steamac-vm`, `./run.sh`, порт 2222) и выключен в
`FX Steam Launcher.app` (ключ `SteamacReleaseDefaults` в Info.plist, ставит `bundle.sh`). При
включении лаунчер генерирует пароль пользователя `steamos` (20 символов, SecRandomCopyBytes),
хранит его в связке ключей отдельно для каждого диска (по GUID его GPT) и на следующей загрузке
передаёт гостю только хеш SHA-512 crypt (диск-«config payload», `steamac.config=1`; гость отвечает
`config applied`). В настройках видны пользователь, пароль (Показать/Скопировать), готовая строка
`ssh -p … steamos@127.0.0.1`, статус «Пароль применён в SteamOS / Пароль будет применён при следующем запуске» и **Создать новый пароль**;
у dev-лаунчера пароль генерируется только кнопкой (диски Docker-сборки сохраняют `steamos`). Диски,
созданные в приложении, получают пароль только так — пароля по умолчанию у них нет. Из терминала:
`steamac-vm --ssh-password <диск>` печатает пользователя, пароль и статус.

### Локальная сеть и Steam Remote Play

Обычная сеть работает через пользовательский NAT gvproxy (SteamOS: `192.168.127.2`);
широковещательные пакеты локальной сети через него не проходят. **Настройки → Дополнительно →
Remote Play в локальной сети** (со следующего запуска) или `--lan-remote-play` включает ретранслятор
обнаружения в лаунчере и проброс с Mac в гостя с сохранением номеров портов:
UDP **27031–27036**, TCP **27036–27037**. По умолчанию **выключено**: переключатель
открывает Remote Play для других машин независимо от SSH. `--no-lan-remote-play`
выключает его на одну загрузку; выключенная Сеть отключает его тоже.

Разрешите доступ macOS к **локальной сети** и входящий трафик в firewall Mac/SteamOS.
Steam Link и Mac должны находиться в **одной подсети IPv4** (изоляция клиентов Wi-Fi,
гостевые сети, VLAN, обнаружение через маршрутизатор и IPv6-only не поддерживаются).
Включите Remote Play в гостевом Steam; для ручного сопряжения используйте LAN-адрес Mac,
не `192.168.127.2`. Steam Link не может разбудить спящую SteamOS: перед подключением разбудите её из окна
на Mac, значком в Dock или контроллером. Отчёты с логами лаунчера содержат состояние и счётчики
ретранслятора, действующие пробросы и лог gvproxy, адреса, маршруты и слушающие сокеты гостя (STEAMAC-9G).
Если порты заняты Steam на Mac, закройте его: лаунчер не разделяет
и не отбирает UDP 27036, пишет `remote-play: disabled for this boot` и убирает свой проброс.
Собственные broadcast Steam на Mac с UDP 27036 не отправляются обратно в гостя.

Ретранслятор сохраняет идентификаторы Steam и неизвестные поля protobuf, заменяет подсказки
адресов в status на LAN IPv4-адрес Mac и сохраняет порты благодаря одноимённому пробросу.
Объявления гостя обновляются настоящими запросами обнаружения раз в пять секунд
(gvproxy не экспортирует самостоятельные broadcast гостевой подсети); если Steam не
отвечает, объявления не выдумываются. Steam без входа в аккаунт может не объявлять хост.
`--selftest-remote-play` проверяет разбор пакетов и замену адресов без запуска ВМ.
Для проверки настоящего LAN-ответа (на Mac или второй машине):
`python3 scripts/test/remote-play-discovery.py --bind <LAN-IP> --broadcast <broadcast-подсети> --expect-host <LAN-IP-Mac>`.
Клиент использует временный порт, печатает реальный ответ Steam и заменённый адрес,
возвращает ошибку при отсутствии ответа; успех не означает проверку сопряжения или стриминга.
Протокол: [требования Valve к сети Remote Play](https://help.steampowered.com/en/faqs/view/3E3D-BE6B-787D-A5D2),
[protobuf удалённого клиента Steam](https://github.com/SteamDatabase/Protobufs/blob/master/steam/steammessages_remoteclient_discovery.proto)
и [формат оболочки discovery](https://github.com/OpenSourceLAN/steam-discover/blob/master/listener.js).

## Трансляция через Moonlight

**Настройки → Трансляция → Включить трансляцию Moonlight** сразу включает встроенный
сервер GameStream; по умолчанию он **выключен** и работает только в оконном процессе ВМ.
Установите [Moonlight](https://moonlight-stream.org/) на устройство в доверенной локальной
сети, разрешите macOS доступ к **локальной сети** и входящие соединения. Выберите этот Mac
в Moonlight (или добавьте LAN-адрес Mac вручную). Введите показанный устройством
четырёхзначный PIN в окне сопряжения на Mac, затем запустите **SteamOS** в Moonlight.

Вкладка «Трансляция» показывает состояние сервера и сеанса, сопряжённые устройства и даты
сопряжения. **Отозвать доступ** удаляет доступ устройства и завершает его текущую трансляцию;
для нового подключения потребуется сопряжение. **Завершить трансляцию** отключает текущий
сеанс, не отзывая доступ. Выключение трансляции закрывает порты и завершает сеанс.
Приостановка ВМ и сон SteamOS тоже останавливают трансляцию и закрывают порты; после
возобновления сервер включится снова, если настройка осталась включённой.
Пока клиент получает трансляцию, настройка паузы игры в фоне не замораживает игру.

Mac слушает TCP **47984, 47989**, пока сервер включён, и TCP **48010** / UDP **47998–48000**
для сеанса; обнаружение Bonjour использует **_nvstream._tcp**. Не открывайте эти порты
в Интернет. Функция независима от **Дополнительно → Remote Play в локальной сети**,
не требует Steam Link, гостевого Steam Remote Play или виртуального монитора.

Передаются экран гостя, включая видимый слой игры DXMT, и звук воспроизведения гостя —
не рабочий стол Mac, оверлеи лаунчера или микрофон. Используются H.264 / аппаратный HEVC
(если поддерживается) и Opus; разрешение записи экрана и драйвер аудиопетли не нужны.
Запрошенное Moonlight разрешение временно задаёт размер экрана гостя (чётный, в пределах
максимума ВМ); после сеанса восстанавливается размер окна, а если «Размер экрана гостя следует
за размером окна» выключен — прежнее разрешение гостя. Одновременно транслирует один
клиент. Клавиатура, мышь, касания как мышь и контроллеры управляют тем же запущенным
гостем вместе с локальным вводом. На время сеанса контроллеры Moonlight занимают первые
слоты игроков SteamOS перед контроллерами Mac; если **Дополнительные контроллеры**
выключены, контроллер Mac ждёт завершения трансляции. После сеанса контроллеры Mac
возвращаются в обычные слоты. HDR, нативные перо/касания и шифрование видео не
предлагаются; используйте доверенную LAN. `--selftest-stream` проверяет компоненты
протокола и медиапотоков без загрузки ВМ.

**ОЗУ ВМ и графика используют одну память Mac.** Автоматический объём ОЗУ ВМ — половина
физической памяти (4–16 GiB). При каждой загрузке лаунчер резервирует ещё минимум 3 GiB
либо четверть памяти Mac для macOS, других приложений и накладных расходов драйвера.
Остаток — бюджет GPU (256 MiB–16 GiB, округляется вниз до 256 MiB). На Mac с 16 GiB это
8 GiB ВМ + 4 GiB GPU + 4 GiB резерв; при пользовательских 9 GiB ВМ графике остаётся 3 GiB.
Настройки → Дополнительно показывает оба бюджета и предупреждает, если графике осталось менее
2 GiB либо суммарный объём превышает память Mac. KosmicKrisp и MoltenVK передают этот бюджет
через device-local heap Venus и, если включено, `VK_EXT_memory_budget`; запросы памяти GL
в zink и DXVK/vkd3d видят уменьшенный heap, а не всю unified memory Mac (STEAMAC-S).
`steamac.gpu_mib=` также обновляет VRAM-report слой Steam. Это ориентир для выбора текстур,
не жёсткий лимит выделения: игра может его игнорировать, а другие приложения Mac — занять
резерв. Тогда уменьшите ОЗУ ВМ или качество текстур.
Для проверки на одноразовой ВМ `--cmdline '… steamac.gpu_mib=3072'` переопределяет бюджет
хоста и гостя; `host/virglrenderer/test/memory_budget.c` запрашивает heap/бюджет и заполняет
реальные GPU-буферы до заявленного размера (с `VN_DEBUG=mem_budget` расширение бюджета
доступно; по умолчанию Venus его отключает). Не запускайте тест выделения на диске разработчика.

**Больше места для игр:** свободное место на Mac не становится автоматически свободным местом
в SteamOS. Размер home задаётся при создании диска. **Настройки → Дополнительно → Увеличить диск…** увеличивает
его без пересоздания диска и удаления игр (только увеличение, до 4096 GiB). Для работающего диска
**Увеличить и перезапустить** штатно выключает SteamOS, берёт эксклюзивную блокировку остановленного диска,
увеличивает образ и запускает ВМ снова. SteamOS расширяет последний раздел home через
`systemd-repart`, затем его ext4 через `x-systemd.growfs` перед использованием. Другие лаунчеры
тоже должны быть остановлены; приостановленная ВМ продолжает владеть диском. APFS / Mac OS Extended
занимают добавленное место по мере записи SteamOS; exFAT занимает весь добавленный объём сразу,
поэтому свободное место проверяется заранее. Из терминала, когда SteamOS остановлена:
`work/out/steamac-vm --grow-disk /path/to/steamos.img --home-gib 128`.

**Меньше ёмкости (уменьшить диск):** **Настройки → Дополнительно → Уменьшить диск…** снижает
ёмкость home, если данные ещё помещаются (иначе отказ). Ext4 нужно сжать **до** GPT/truncate:
one-shot загрузка с `steamac.shrink-home=N` и `steamac.slot=stop` делает `e2fsck`/`resize2fs` в
initramfs, гасит ВМ, затем хост переписывает GPT и усекает образ. Если файловая система уже
влезает — хост усекает сразу. Терминал (ФС уже влезает, SteamOS остановлена):
`work/out/steamac-vm --shrink-disk /path/to/steamos.img --home-gib 192`.

**Вернуть место на Mac:** после удаления игр (или большого Grow) разреженный `steamos.img` может
оставаться большим на диске, хотя SteamOS эти блоки уже не использует. **Настройки → Дополнительно →
Освободить место на диске…** (SteamOS запущена) просит гостя сделать `fstrim` для `/home` (и `/var`,
если смонтирован); virtio-blk DISCARD пробивает дырки в образе на Mac. Ёмкость не меняется —
выделенный размер может уменьшиться **только если образ находится на APFS**. На HFS+ и exFAT
этот способ не освобождает место; лаунчер проверяет том до запуска. Клоны и снимки APFS могут
сохранять освобождённые блоки, поэтому свободное место на Mac не обязательно вырастет на столько же.
Уменьшить диск меняет ёмкость; Освободить место только пробивает дырки.

Для тестов: `STEAMAC_DEFAULTS_DOMAIN=<домен>` подменяет домен настроек; `--selftest-settings
--selftest-out DIR` открывает окно без ВМ и пишет PNG каждой вкладки; в `--control-fifo` есть
`settings TAB`, `settings-dump PNG`, `set KEY VALUE` (как из окна), `restart`.

### Профили отдельных игр

В **Настройки → Игры** хранится профиль для каждого Steam app id, отдельно от авто-захвата мыши:
**Графика** — По умолчанию (= Vulkan) / Vulkan / DXMT; **Драйвер Vulkan** — По умолчанию
(глобальный драйвер) / KosmicKrisp / MoltenVK (предлагаются только доступные драйверы);
**Параметры запуска** — разделённые пробелами слова `NAME=value` перед `%command%`, а не произвольные
команды оболочки. Вся строка — не более 256 символов. Имена начинаются с `VKD3D_`, `DXVK_`,
`PROTON_`, `WINE_`, `MESA_`, `RADV_`, `VK_`, `DXMT_`, `MTL_`, `STEAMAC_`, за префиксом — ноль
или больше символов `[A-Z0-9_]`; значения соответствуют `[A-Za-z0-9_.,:;+-]*` (пустое допустимо).
Присваивания сортируются по имени; при повторе имени побеждает последнее. Неверный ввод остаётся
видимым с сообщением об ошибке и не сохраняется и не отправляется. Пустое поле значит, что профиль не
добавляет переопределений (в поле больше нет примера `VKD3D_CONFIG=dxr`, который выглядел как
принудительное значение, STEAMAC-8X). Metal Performance HUD показывает размер drawable на Mac, он может
отличаться от разрешения рендеринга игры.

**Рекомендуется: … — Применить** получает профиль из сервиса статистики с ограничениями
**Мой Mac** этого компьютера (ядра GPU, ОЗУ и производительные ядра — не больше, чем у него).
Конфигурации ранжируются по `(работает хорошо + 0.5 × играбельно с проблемами) / все оценки`,
затем по большей доле успешных запусков и меньшей доле ранних выходов; нужны хотя бы две разные
установки (подробности в «Статистика игр»). Рекомендации не применяются автоматически:
профиль меняется только кнопкой **Применить**.

Для DXMT нужны **Настройки → Дополнительно → Разрешить DXMT (D3D11 через Metal на Mac)** и
загрузка ВМ с этим разрешением. Пока оно выключено, профиль DXMT помечен как не действующий и
предлагает **Разрешить DXMT…** с прежним предупреждением о безопасности; при загрузке только с
Vulkan такой профиль не может выбрать для игры инструмент совместимости DXMT.
Vulkan-драйвер выбирается **на загрузку ВМ**, а не на процесс. Если запускается или получает фокус
игра с другим драйвером в профиле, лаунчер предлагает перезапустить ВМ с ним и снова запустить игру,
когда Steam будет готов. Это разовое переопределение не меняет глобальную настройку драйвера.

Профили передаются по двустороннему порту `fx.progress` (одно сообщение на строку). Хост → гость:
`profiles <base64 от UTF-8 JSON>` заменяет весь набор при первом heartbeat/ready агента за загрузку
и после изменений; `launch <appid>` запускает `steam steam://rungameid/<appid>` от пользователя
сессии; `restart-steam` перезапускает `steam.service` только с согласия пользователя. Формат:
`{"v":1,"games":{"570":{"gfx":"dxmt","env":"PROTON_LOG=1"}}}`; поля по умолчанию/пустые опускаются,
`driver` остаётся на хосте. Гость атомарно сохраняет набор в `~/.config/steamac/game-profiles.json`.
Перед подготовкой графики и параметров игр ExecStartPre `steam-profiles-wait` ждёт синхронизации
этой загрузки до 5 с, затем фиксирует последний доступный набор (при тайм-ауте — из сохранённого
файла). Гость → хост: `profiles-ok <sha256 JSON> applied|pending`; `pending` означает, что Steam
работает с другим применённым набором, и лаунчер предлагает **Перезапустить Steam** или **Позже**.
`game-gfx <appid> dxmt|vulkan` следует за `game-proton` и описывает фактический графический путь
Proton по его маркеру `.steamac-dxmt`, а не по разрешению при загрузке.
Неизвестные команды по-прежнему игнорируются для совместимости старых/новых хоста и гостя.

При старте Steam слова из профиля заменяют встроенную запись `steam-title-defaults`; без `env`
в профиле Dragon's Dogma 2 сохраняет значение по умолчанию с проверкой возможностей Venus.
Правила владения прежние: последующая правка пользователя в Steam побеждает; замена или удаление
слов, которыми владеет steamac, не накапливает старые присваивания, а удаление возвращает прежние
параметры запуска.

## Приостановка (Suspend)

**Как:** Настройки → Основные → «При закрытии окна» → **Приостановить** — тогда закрытие окна
приостанавливает ВМ вместо выключения; или меню **FX Steam Launcher → Приостановить** (Ctrl+Cmd+S,
работает и когда клавиатура у гостя). `krun_pause` (патч libkrun 0016) останавливает все vCPU и
звук гостя, окно прячется, в строке меню появляется значок ⏸: «SteamOS приостановлена», с какого
времени и сколько памяти занято, **Возобновить**, **Выключить SteamOS**. Приостановленная ВМ не тратит
CPU (~0 %), Mac может засыпать.

**Возобновление:** щелчок по иконке в Dock, повторный запуск приложения (Finder, `open`, `open -a`),
значок в строке меню или меню → **Возобновить**. Окно возвращается (и полноэкранный режим, если был),
захват мыши восстанавливается; плашка «Возобновление…» держится до первого нового кадра гостя (если
GPU гостя простаивает, как у неподвижного интерфейса Steam, — 0,5 с; максимум 2,5 с).

**Часы:** монотонные часы гостя паузу не видят (libkrun сдвигает виртуальный таймер, как QEMU) —
планировщик sched_ext и watchdog'и не срабатывают. Настенные часы сразу после возобновления
выставляет `fx-clock-sync.service` (root-сервис слоя, тот же бинарник `fx-progress-agent
clock-sync`, запускается udev при появлении порта): лаунчер пишет своё время `time <unix_ns>` в
virtio-порт `fx.clock`, сервис сдвигает только CLOCK_REALTIME (`clock_adjtime(ADJ_SETOFFSET)`,
только вперёд и только если отстаёт больше чем на 1 с), после шага timesyncd синхронизируется сам.

**Выход:** Cmd+Q / Dock → Завершить во время приостановки спрашивает «SteamOS приостановлена»:
**Выключить SteamOS** (гость возобновляется и штатно выключается) или **Отменить** (остаётся
приостановленным). Выход из учётной записи, перезагрузка и выключение Mac не спрашивают.

**Ограничения:** состояние живёт только в памяти, пока работает FX Steam Launcher, — на диск оно
не сохраняется (память гостя и состояние GPU хоста — virglrenderer, MoltenVK, Metal — не
сериализуются). Выход из приложения, его сбой, выход из учётной записи или выключение Mac — это
обычное выключение SteamOS, несохранённый прогресс игры теряется. Вся память гостя остаётся
занятой, пока ВМ приостановлена. Сетевые соединения гостя (онлайн-игры, загрузки) после долгой
паузы могут оборваться и переподключиться.

## Сон SteamOS (Sleep)

Steam → Power → **Sleep**, автосон Steam по простою (Settings → Power → «Sleep after», по
умолчанию 1 час) и `systemctl suspend` в госте не усыпляют ядро гостя (s2idle в ВМ разбудить нечем —
раньше SteamOS так и висел до выхода из приложения). Слой подменяет `ExecStart` у
`systemd-suspend.service` (и `systemd-suspend-then-hibernate` / `systemd-hybrid-sleep` — то же
самое; гибернация выключена в `sleep.conf.d`) на `fx-progress-agent sleep`: он выполняет хуки
`system-sleep` (`pre`), пишет `sleep <action> <token>` в virtio-порт `fx.sleep` и ждёт ответа.
Лаунчер приостанавливает ВМ (`krun_pause`, как Приостановить — CPU ~0 %, Mac может засыпать), но окно
остаётся: поверх кадра — карточка «SteamOS в режиме сна». Щелчок, клавиша, кнопка геймпада или
иконка в Dock будят: `krun_resume`, гостю уходит `wake <token> <unix_ns>`, команда сдвигает
настенные часы (как clock-sync), выполняет хуки `post` и завершается — logind шлёт
PrepareForSleep(false), Steam просыпается; плашка «Выход из режима сна…» держится до первого кадра. Щелчок или
клавиша, разбудившие гостя, в гостя не попадают.

Закрытие окна во время сна — по «При закрытии окна»: Приостановить прячет окно (Возобновить потом и
будит), Выключить SteamOS / Cmd+Q будят гостя и нажимают кнопку питания, когда задача сна в госте закончилась
(`awake <token>`; пока она идёт, logind кнопку игнорирует). Без порта (`--headless`, старый лаунчер)
сон в госте завершается ошибкой, а не засыпанием.

Для тестов в `--control-fifo`: `close`, `suspend`, `resume` (будит и спящего гостя), `reopen`,
`quit`, `wake` (как пробуждение Mac), `quit-prompt shutdown|cancel|dump PNG`,
`status open|close|dump PNG|item TITLE`.

## Режим рабочего стола (Desktop Mode)

Steam → Power → **Switch to Desktop** запускает KDE Plasma; значок **Return to Gaming Mode** на рабочем
столе возвращает обратно. В образе Steam Frame этот режим — VR-стол (`plasma-session.target` хочет
SteamVR, который в ВМ замаскирован), поэтому слой его заменяет: `plasma-session.target` и
`steamac-nested-desktop.service` запускают Plasma одним окном KWin внутри того же gamescope
(`/usr/lib/steamac/nested-desktop`, как `steamos-nested-desktop` Valve) размером с дисплей, так что
gamescope показывает его 1:1. `gamescope-onready` ждёт этот сервис: когда Plasma завершается, сессия
заканчивается и SDDM входит заново. У Plasma свой runtime-каталог и своя сессионная шина D-Bus;
прослойка `steamosctl` из слоя (`/usr/lib/steamac/desktop-bin`, первой в её PATH) отправляет команды
SteamOS, например Return to Gaming Mode, на внешнюю шину, где работает steamos-manager. Автозапуск
Steam на рабочем столе (`/usr/lib/steamac/desktop-xdg/autostart/steam.desktop`) сохраняет клиент,
выбранный в лаунчере, вместо штатного `-deckard` (клиент Frame), из-за которого при каждом
переключении скачивался бы другой клиент. Агент прогресса сообщает `focus desktop <w>x<h>` (окно
Plasma): лаунчер оставляет относительную мышь и переносит её на это окно так, как его масштабирует
gamescope, а загрузка сразу в рабочий стол (`steamos-session-select plasma-persistent`) сообщает
`ready`, когда стол появился.

**Раскладки клавиатуры.** С «Настройки > Основные > **Раскладки клавиатуры Mac в режиме рабочего
стола**» (по умолчанию вкл., применяется сразу) в режиме рабочего стола те же раскладки, что
включены на Mac, в порядке меню ввода, и они переключаются вместе с источником ввода Mac (клавиша
глобуса, Control-пробел). Лаунчер переводит каждую в раскладку XKB (`com.apple.keylayout.Russian` →
`ru(mac)`, `RussianWin` → `ru(winkeys)`, `German` → `de(mac)`, …; иначе — только по закрытому списку
однозначных первых языков; неизвестные источники пропускаются; метод ввода считается раскладкой,
которой он печатает). Отправляется не более четырёх раскладок (лимит XKB), обязательно с активной:
`keyboard-layout <индекс активной> <раскладка(вариант)>…` по `fx.progress` при каждой смене и
каждый раз, когда фокус получает режим рабочего стола, и ещё раз через 1,5, 4 и 8 с (при старте
Plasma выбирает свою первую раскладку уже после того, как KWin взял нашу). Агент запускает
`/usr/lib/steamac/desktop-keyboard` (только последний запрос, не блокируясь): он проверяет раскладки
и варианты по XKB гостя, отбрасывает неизвестные и пересчитывает активный индекс (если активная
отброшена, не переключает). Как формат часов Mac, следует за Mac, пока раскладки не изменены в
SteamOS: первая синхронизация заменяет даже прежний пользовательский список; затем замеченная
правка раскладок Plasma пользователем навсегда получает приоритет. Маркер —
`~/.config/steamac/mac-keyboard.json`; выключение настройки останавливает синхронизацию, но не
возвращает прежний список. Пока синхронизация действует, скрипт пишет `kxkbrc` (с пустым
`DisplayNames`), просит KWin перечитать его при изменении файла или несовпадении кодов раскладок
KWin (`reloadConfig` на `org.kde.keyboard` `/Layouts`) и выбирает активную
(`org.kde.KeyboardLayouts.setLayout`) на живой шине вложенного сеанса
(`nested_plasma/steamac-session-bus`; без шины или с устаревшей шиной ничего не делает). Уведомление
macOS после переключения глобусом часто приходит через 0,55–0,85 с, поэтому опрос текущей раскладки
каждые 30 мс работает только при включённой настройке, фокусе рабочего стола и активном лаунчере.
Клавиши остаются физическими клавишами Mac (коды evdev), а что они печатают, решает раскладка.
Игровой режим свою раскладку не меняет.

Flatpak-приложения (Discover) работают в bubblewrap, который монтирует свой procfs в user namespace.
Ядро разрешает это, только пока в пространстве монтирования есть полностью видимый procfs, а initramfs
накрывает настоящий `/proc/cmdline` синтезированным; поэтому он ещё монтирует нетронутый procfs в
`/run/steamac/proc` (`nosuid,nodev,noexec`). Без него каждое Flatpak-приложение завершается с
`bwrap: Can't mount proc on /newroot/proc: Operation not permitted`.

## Буфер обмена (Clipboard)

Настройки → Основные → **Общий буфер обмена со SteamOS** (по умолчанию вкл., применяется сразу): текст
(UTF-8) и PNG-изображения, скопированные на Mac, вставляются в SteamOS (Ctrl+V — в текстовые поля
Steam, в игры и приложения Desktop Mode) и обратно; ограничения — 1 МиБ текста и 16 МиБ на
изображение (больше — пропускается со строкой в логе). Элементы, которые менеджеры паролей помечают
как скрытые или временные (`org.nspasteboard.ConcealedType` / `TransientType`), остаются на Mac, пока
не включено **Включить скрытые данные (менеджер паролей)**. Лаунчер проверяет `changeCount`
буфера таймером 0,5 с только пока приложение активно и VM работает, и один раз при каждой активации —
никогда в фоне, при приостановке или сне; изображения из SteamOS попадают на Mac как PNG + TIFF.

Транспорт: virtio-console порт `fx.clipboard`, двоичные кадры (`HELLO` / `STATE` / `SET` с
порядковыми номерами / `ACK`; `host/launcher/Sources/steamac-vm/Clipboard.swift`,
`guest/progress-agent/src/clipboard.rs`). В госте пользовательский сервис
`fx-clipboard-agent.service` (`fx-progress-agent clipboard`, его хотят и игровая сессия, и Desktop
Mode) владеет `CLIPBOARD` и следит за ним (XFixes; TARGETS, UTF8_STRING, text/plain;charset=utf-8,
TEXT, STRING, image/png, INCR больше 256 КиБ) на **обоих** Xwayland-серверах gamescope (`:0` Steam,
`:1` игры): gamescope сам синхронизирует между ними простой текст, перехватывая выделение, но не
изображения и не текст размером под INCR. В Desktop Mode используется ещё Wayland-буфер сессии
Plasma через `zwlr_data_control_manager_v1` (`ext_data_control_manager_v1`, если есть); KWin
передаёт его X11-приложениям, пока активно X11-окно. Подавление эха — по содержимому: каждая
сторона помнит последнее отправленное или принятое содержимое, так что одно копирование — одна
передача, сколько бы раз gamescope, KWin или Klipper его ни переобъявляли. Выделение, уже бывшее на
дисплее при его появлении (например, история, восстановленная Klipper), на Mac не отправляется —
туда предлагается общее содержимое. В `--control-fifo` есть `chord KEYCODE ctrl` (например,
`chord 9 ctrl` = Ctrl+V в госте) и `set shareClipboard on|off`.

## Общая папка

**Настройки → Дополнительно → Общая папка** (со следующего запуска) открывает SteamOS одну папку Mac
как устройство virtio-fs с меткой `macshare`, монтируемое по пути **Точка монтирования в SteamOS**
(по умолчанию `/home/steamos/MacShare`) при каждой загрузке. Файлы читаются и пишутся на месте,
ничего не копируется: игры, хранящиеся на Mac, загружаются со скоростью диска Mac, а записанное из
SteamOS сразу есть на Mac. По умолчанию выключено (папка не выбрана). Командная строка: `--share DIR`,
`--share-mount PATH`, `--no-share` на один запуск.

**Использовать как библиотеку Steam** включено по умолчанию при выбранной общей папке
(со следующего запуска). SteamOS создаёт **`<точка монтирования>/SteamLibrary/steamapps`** и
регистрирует `<точка монтирования>/SteamLibrary` до запуска Steam: диалог «Добавить диск»
в Desktop Mode не нужен. В настройках хранилища Steam и выборе места установки это вторая
библиотека **Mac Share**, а не съёмный диск Deck, требующий форматирования.
`--share-library` / `--no-share-library` меняет выбор на один запуск; выключение не удаляет
файлы и уже зарегистрированную библиотеку.

Регистрация происходит **один раз для каждого гостевого пути библиотеки**. Если затем удалить
её в Steam, она не добавится снова даже после выбора другой папки и возврата. Маркер —
`~/.local/share/Steam/config/steamac-share-library.json` рядом с `config.vdf`; чтобы снова
добавить удалённый путь автоматически, уберите его из маркера при остановленном Steam.
Смена только папки Mac при прежней гостевой точке монтирования не запускает регистрацию повторно.

**Файловая система: рекомендуется APFS.** Proton хранит Windows-префиксы в
`steamapps/compatdata` каждой библиотеки; им нужны символьные ссылки, а не просто запись файлов.
Хук пробует создать и прочитать симлинк в смонтированной папке от `steamos`; если это не удалось,
регистрация пропускается (в том числе на exFAT, где симлинков нет). Mac OS Extended/HFS+
поддерживает симлинки и не исключается по имени файловой системы. В ВМ проверены чтение/запись,
chmod на APFS через virtio-fs и симлинки `dosdevices/c:` / `z:` префикса Proton 11 ARM64.
Обычная регистронезависимая APFS остаётся такой и в Linux: играм с разными файлами, отличающимися
только регистром, нужен регистрозависимый том или внутренняя библиотека ВМ. Это не преобразование
Mac/Windows-библиотеки Steam в Linux-библиотеку; выделите отдельную папку для SteamOS.

Реализация: `steam-share-library` — неблокирующий `ExecStartPre` у `steam.service`, включаемый
через `steamac.share_library=1` вместе с `steamac.share=PATH`. До любых изменений он проверяет
**именно точку монтирования** через `findmnt -t virtiofs`. Проверенный Deck-клиент (1792618285)
сначала читает `~/.local/share/Steam/steamapps/libraryfolders.vdf`, при его отсутствии —
`config/libraryfolders.vdf`, и переписывает оба как одинаковые копии. Хук атомарно меняет основной
файл, сохраняя существующие нумерованные записи (или импортируя старый файл), и задаёт только
`path` и `label`. `contentid`, `totalsize` и `apps` заполняет сам Steam; выдуманных ID и записей
об установленных играх нет. Если ранее зарегистрированная папка не подключена, Steam **сохраняет
запись, но пишет «Install folder … not mounted»**; место установки недоступно до возврата папки.
В этом случае хук не трогает список и маркер и не создаёт подменную библиотеку на гостевом диске.
Подключайте внешний том до запуска ВМ; если его не было — подключите и перезапустите.

Лаунчер добавляет устройство через `krun_add_virtiofs4` (`KRUN_SEMANTICS_LINUX_SIMPLIFIED`: гость
видит на каждом файле свои uid/gid, так что пользователь `steamos` читает и пишет без сопоставления
владельцев; без окна DAX) и передаёт `steamac.share=PATH` в командной строке ядра. Initramfs
(раздел «shared folder») проверяет путь — подкаталог `/home/steamos/`, без пустых компонентов,
`.` и `..`, только `[A-Za-z0-9/_.-]` — и создаёт runtime-юнит монтирования
(`/run/systemd/system/<path>.mount`, `What=macshare`, `Type=virtiofs`, `TimeoutSec=15`), wanted от
`multi-user.target`. Юнит требует и ждёт `steamos-create-homedir.service`, перед пользовательскими
сессиями: на свежем диске SteamOS должна создать и заполнить домашнюю папку до создания точки
монтирования systemd, иначе дом останется root-owned, а копирование шаблона будет пропущено.
`DefaultDependencies=no` убирает порядок перед `local-fs.target` (дом создаётся позже); обычный
порядок размонтирования при выключении сохранён. Сбой общей папки не препятствует загрузке.
Юнит живёт только эту загрузку, как и runtime-маски юнитов. Папка, которой нет при запуске
(внешний диск отключён, переименована), пишется в лог и пропускается — лаунчер стартует без общей
папки; отказывается стартовать только явный `--share`. В настройках строка показана красным как
не найденная.

**Безопасность.** По модели безопасности libkrun virtio-fs не ограничивает гостя общей папкой: на
macOS lookup не отфильтровывает `..`, а лаунчер не в песочнице. С включённой общей папкой root в
SteamOS (всё, что получит там root: игра, Flatpak, эксплойт в Proton) потенциально может прочитать
всё, что доступно вашему пользователю Mac, и писать туда, куда может он. Открывайте папку только
той SteamOS, которой доверяете, и выключайте, когда она не нужна. SSH тут ни при чём.

## Контроллер

Любой контроллер, который поддерживает GameController в macOS (Xbox, DualSense, DualShock 4, MFi, …),
ведёт геймпад в SteamOS: первый подключённый или выбранный в «Настройки → Контроллер» — игрок 1,
остальные — игроки 2–4 («Несколько контроллеров» ниже). Это не virtio-input
устройство: лаунчер передаёт его по порту virtio-console `fx.pad` root-сервису гостя
`fx-pad.service` (`fx-progress-agent pad`, его запускает udev, когда порт появляется), а тот создаёт
его через uinput. Поэтому он следует за Mac, пока ВМ работает: появляется, когда контроллер
подключается (Steam показывает «Controller Connected»), исчезает вместе со своим контроллером и меняет вид
вместе с ним. Настройки → Контроллер → **Отображается в SteamOS как** (`--pad auto|xbox360|dualsense|dualshock4|steamcontroller`
на один запуск):

- **Автоматически** (по умолчанию): того же вида, что и ведущий контроллер — DualSense (или Edge) →
  DualSense, DualShock 4 → DualShock 4, любой другой → контроллер Xbox 360; Steam Controller
  передаётся в SteamOS как есть («Проброс Steam Controller» ниже);
- **Контроллер Xbox 360**: то, что показывает драйвер ядра `xpad` (`045e:028e`);
- **DualSense** / **DualShock 4**: то, что показывают `hid-playstation` / `hid-sony` для USB-pad
  (`054c:0ce6` / `054c:09cc`, версия `0x8111`, кнопки по положению, цифровые L2/R2 рядом с
  аналоговыми курками). SDL в Steam сопоставляет его как контроллер PS5 / PS4 и показывает значки
  PlayStation;
- **Steam Controller**: Steam Controller передаётся в SteamOS как есть, любой другой контроллер
  ведёт контроллер Xbox 360.

**Диагностика Home / PS.** Лаунчер просит macOS оставить эту кнопку SteamOS, но система может
не учесть пожелание. Если по USB кнопка работает, а по Bluetooth — нет, сравните индикатор
**Home** в «Настройки → Контроллер» и отправьте отчёт после нажатия и отпускания кнопки
при каждом подключении. Лог фиксирует наличие Home в GameController, привязку к системному
жесту, вызовы обработчиков кнопки и профиля и постановку события в очередь порта pad гостя; `pad state`
также показывает состояние Home. Это отделяет проблему ввода на Mac от доставки гостю:
сбой Bluetooth не обязательно связан с пробросом DualSense (DualShock 4 использует виртуальный pad).
`pad state`, а также `controllers.txt` в отчёте о проблеме с логами лаунчера содержат пассивный список HID
(ID, имена, транспорт, usage и почему устройство пробрасывается или нет; исключённые устройства не
открываются, разрешение «Мониторинг ввода» не запрашивается) и последний снимок стиков, сырых датчиков
движения и касаний DualSense с его возрастом (STEAMAC-8R/8V).

**Вибрация.** У pad есть `FF_RUMBLE`, как у настоящих драйверов, так что SDL и Steam им вибрируют —
игры через Steam Input доходят до него через виртуальный Xbox-pad Steam. Воспроизведение uinput
оставляет драйверу в user space: `fx-pad` повторяет правила ff-memless ядра (задержка, длительность,
повторы, повторная загрузка, сложение эффектов) и отправляет лаунчеру итоговый уровень
`rumble <strong> <weak>`, а тот играет его через haptics GameController: сильный мотор — на левой
рукояти, слабый — на правой (у контроллеров без раздельных рукоятей — один уровень на всё); пока ВМ
приостановлена — ничего. Протокол порта — в `guest/progress-agent/src/pad.rs`. Сенсорная панель,
гироскоп, световая панель и адаптивные курки — HID-функции настоящего контроллера, которых у этого
evdev-устройства нет.

**Проброс DualSense.** Когда pad ведёт DualSense (или Edge) и он виден как DualSense, Настройки →
Контроллер → **Передавать DualSense напрямую** (по умолчанию включено, применяется сразу) отдаёт SteamOS
сам контроллер вместо uinput-pad. Лаунчер открывает его как сырое HID-устройство (IOHIDManager, без
захвата: GameController по-прежнему выбирает его и будит спящего гостя), а `fx-pad` воссоздаёт его
через `/dev/uhid` с тем же дескриптором отчётов, vendor/product и шиной USB или Bluetooth. Драйвер
гостя `hid-playstation` цепляется к нему, как к подключённому контроллеру (геймпад, сенсорная
панель, датчики движения, световая панель и индикаторы игрока, индикатор mute), а Steam работает с
`/dev/hidraw*` своим HIDAPI-драйвером DualSense: Steam Input получает сенсорную панель, гироскоп и
кнопку mute и сам управляет вибрацией, световой панелью и адаптивными курками. Входные отчёты идут в
гостя как есть (`hid-input`); выходные отчёты, GET_REPORT и SET_REPORT — обратно в контроллер
(`hid-output`, `hid-get` / `hid-get-reply`, `hid-set` / `hid-set-reply`, hex с ID отчёта в начале).
Если гость не успевает, старые входные отчёты отбрасываются, а не копятся: каждый несёт всё
состояние. Перестановка A/B и мёртвая зона к проброшенному контроллеру не применяются. GameController
не сообщает, какое HID-устройство соответствует контроллеру: при нескольких DualSense пробрасывается
первый найденный. Старые слои гостя без `caps hid` по-прежнему получают uinput-pad.

**Обычные HID-джойстики и геймпады.** Режим **Автоматически** также передаёт как есть устройства
Generic Desktop (usage page 1): Joystick (4) и Game Pad (5), которые
не публикует GameController, например DJI FPV Remote Controller 2 (`2ca3:1020`) и Spektrum SLT6
(`35cf:04fb`). Существующий путь raw-HID/uhid сохраняет дескриптор, ID и отчёты; раскладку и
калибровку обрабатывают `hid-generic`, SDL и Steam в госте. Это не эмуляция Xbox: настраивайте
устройство в SteamOS/Steam Input, а не в живом тесте GameController, перестановке A/B или мёртвой
зоне лаунчера. Нужен актуальный слой гостя с `caps hid`.
Multi-axis Controller (8), например SpaceMouse, намеренно не сопоставляется по умолчанию.

Устройство занимает свободного игрока с наименьшим номером, чей сервис гостя поддерживает HID,
и делит четыре места с GameController и Steam Controller (для игроков 2–4 включите
**Дополнительные контроллеры**). Оно сохраняет свободное место, но уступает контроллеру
GameController и переходит к следующему свободному игроку либо ждёт, если мест нет.
Резервации BLE Steam Controller остаются липкими и не вытесняются. Обычный HID не резервирует
игрока на старом госте без `caps hid` и не может разбудить приостановленную ВМ. Выключите
**Виртуальный контроллер** (`--no-gamepad`) или выберите явный тип в **Отображается в SteamOS как**,
чтобы прекратить поиск и проброс обычных HID. `pad state` показывает имя, VID/PID, registry ID и игрока.

Чтобы исключить двойной ввод, обычный HID считается принадлежащим GameController только если
`GCController.supportsHIDDevice` возвращает true (с кэшем по registry ID) **и** у опубликованного
элемента `GCController.controllers()` значение `vendorName` или `productCategory` точно совпадает
с product, manufacturer или «manufacturer product» HID, без учёта регистра и с нормализацией пробелов.
Публичной связи контроллера с HID нет: это сопоставление имён, а не догадка по VID/PID.
Поддерживаемое устройство ждёт асинхронной публикации **2 секунды** после обнаружения, не открываясь;
без совпадающего контроллера оно затем пробрасывается как обычный HID, в том числе DJI C5,
даже если macOS заявляет поддержку. Позднее подключение совпадающего GC-контроллера освобождает
обычный HID до назначения игроков; отключение снова предлагает HID для проброса.
Ожидание, допуск и пропуск/освобождение ради GC записываются в лог один раз на переход с VID:PID и product.
DualSense и Valve остаются на прежних маршрутах. Поиск
использует IOHIDManager с независимыми устройствами: сопоставление не открывает посторонние
устройства и не запрашивает «Мониторинг ввода». Обычным коллекциям джойстика/геймпада разрешение
не нужно; подключённый составной контроллер с коллекциями клавиатуры/мыши/трекпада может его потребовать,
и запрос возможен только при открытии уже отобранного контроллера. Apple помечает эти коллекции
в [IOHIDDevice](https://github.com/apple-oss-distributions/IOHIDFamily/blob/main/IOHIDFamily/IOHIDDevice.cpp),
а [плагин устройства](https://github.com/apple-oss-distributions/IOHIDFamily/blob/main/IOHIDLib/IOHIDDeviceClass.m)
запрашивает доступ при открытии, а не при сопоставлении usage.

**Проброс Steam Controller.** Когда **Отображается в SteamOS как** — «Автоматически» или
«Steam Controller», Steam Controller (2026) передаётся в SteamOS как есть тем же путём через uhid, и
Steam сам ведёт его трекпады, гироскоп, задние кнопки и вибрацию своим драйвером. Один — игрок 1;
с включёнными **Дополнительными контроллерами** Steam Controller рядом с другим контроллером
(например DualSense на игроке 1) становится следующим свободным игроком, а не отбрасывается:
- подключён к маку по Bluetooth LE (`28de:1303`): передаётся со своими ID и шиной Bluetooth.
  GameController его не показывает, поэтому контроллер GameController ему не нужен, и он не может
  разбудить спящего гостя (пока ВМ на паузе, HID-ввод отбрасывается);
- через свой Puck (`28de:1304`): интерфейсы 2–5 Puck — слоты контроллеров с дескриптором самого
  контроллера. SDL и Steam принимают контроллеры Puck только по номеру USB-интерфейса, которого у
  uhid-устройства нет, поэтому слот, по которому идёт состояние контроллера, передаётся в SteamOS
  как проводной Steam Controller (`28de:1302`, шина USB); слот без состояния контроллера дольше
  2 с снова убирается (контроллер выключен, ушёл в другой слот или на Bluetooth), и его место
  занимает pad GameController от Puck. В **Desktop Mode** пауза 30 с, а все входные отчёты,
  кроме статуса беспроводного соединения, держат слот живым, включая клавиатуру/мышь lizard-режима
  и отчёты батареи. Так Valve-passthrough остаётся стабильным на рабочем столе, в том числе после
  пробуждения контроллера кнопкой Options. Статус беспроводного соединения не продлевает ни один
  тайм-аут, а статус Disconnect немедленно убирает слот в обоих режимах. Переход в Desktop Mode
  не оживляет слот, уже истёкший по тайм-ауту Gaming Mode в 2 с. Steam Controller этого игрока
  пробрасывается только если ровно у одного игрока контроллер GameController — Steam Controller
  и ровно один слот Puck активен; иначе эти игроки получают uinput-pad, поскольку надёжно
  сопоставить слоты и контроллеры нельзя.

В его дескрипторе есть коллекции клавиатуры и мыши (режим рабочего стола контроллера), поэтому
macOS открывает его только с Системные настройки → Конфиденциальность и безопасность →
**Мониторинг ввода**: лаунчер запрашивает разрешение и открывает устройство, как только оно выдано
(`hid passthrough: Input Monitoring granted, reopening the HID manager`). 64-байтный feature report 1 (командный канал Steam)
Steam Controller по Bluetooth LE macOS возвращает как 65 байт, поэтому запас сверх размеров из дескриптора
есть только у буферов GET_REPORT этого контроллера по Bluetooth; DualSense по USB получает ровно размеры
дескриптора (с запасом его firmware report 32 в 1.9.9 не отвечал, STEAMAC-84). Отключённый контроллер
удаляется по ссылке на устройство, которую держит лаунчер, поэтому после переподключения по USB или
Bluetooth передаётся новое устройство.
Когда контроллеру нужно это разрешение, Настройки → Контроллер показывают предупреждение
с кнопкой **Mac: Мониторинг ввода…**, которая запрашивает доступ и открывает нужный раздел Системных настроек.
Предупреждение видно только при включённом сопоставлении Steam Controller или универсальных HID-контроллеров.
Если доступ уже включён, но контроллер всё ещё недоступен, перезапустите лаунчер.

**Несколько контроллеров.** С «Настройки → Контроллер → **Дополнительные контроллеры**» (включено
по умолчанию, применяется сразу) остальные подключённые контроллеры становятся игроками 2–4, у
каждого свой геймпад в SteamOS — для совместной игры на одном экране. У каждого игрока свой порт
virtio-console: `fx.pad` у игрока 1, как описано выше, и `fx.pad2` … `fx.pad4`, каждый обслуживает
экземпляр `fx-pad@.service` с именем порта (тот же `fx-progress-agent pad` с `FX_PAD_PORT`, его
запускает udev), поэтому протокол на порту одинаков для всех игроков, а вибрация pad играет на том
контроллере, который его ведёт. Игрок получает контроллер, когда сервис гостя на его порту сказал
`hello`: слой гостя без `fx-pad@.service` остаётся с одним pad. Контроллер, выбранный в настройках, —
игрок 1, если это место уже не занял Bluetooth LE Steam Controller. Контроллер остаётся за игроком,
пока не отключится (остальные не сдвигаются), а переподключённый занимает первое свободное место.
Bluetooth LE Steam Controller тоже сохраняет место: отключение игрока с меньшим номером не
сдвигает его вверх, а новый контроллер GameController его не вытесняет. Отключение BLE-контроллера
освобождает место; при переподключении он занимает доступное свободное место с наименьшим номером.
**Отображается в SteamOS как**, перестановка A/B и мёртвая
зона действуют на все pad (при «Автоматически» каждый pad того же вида, что и его контроллер). Пробрасывается только DualSense игрока 1, и только пока у другого игрока не DualSense
(GameController не сообщает, какое HID-устройство чьё): тогда оба получают uinput-pad. Steam
Controller пробрасывается любому свободному доступному игроку (см. выше). Пока ВМ
работает, проверка ввода в «Настройки → Контроллер» помечает каждый контроллер его игроком
(**Игрок 2**). Выключено: используется только игрок 1; BLE Steam Controller не вытесняет уже
занявший место контроллер GameController, а новый контроллер GameController ждёт, если место уже занял BLE.

Тестовые команды `--control-fifo`: `pad on` (pad без контроллера, как в `--input-selftest`),
`pad off`, `pad test` (A + левый стик) — каждая принимает номер игрока (`pad on 2`; без номера — 1) —
и `pad state` (pad гостя, последний уровень вибрации, принимает ли гость HID-устройства,
подключённые DualSense и Steam Controller и число проброшенных входных отчётов).

## FX Steam Launcher.app

`host/launcher/build.sh` (и `./build.sh host`) кроме `work/out/steamac-vm` собирает
`work/out/FX Steam Launcher.app` (`host/launcher/bundle.sh`): `es.fxgam.steamac`, библиотеки
(libkrun, libvirglrenderer, libMoltenVK, libepoxy) в `Contents/Frameworks` через `@rpath`,
в `Contents/Resources` — gvproxy, ядро `Image`, `initramfs.cpio.gz`, `steamac-layer.img`, desync и
CA Valve для создания диска (лицензии — в `Resources/licenses`), иконка: `host/launcher/AppIcon.icon`
(документ Icon Composer) `actool` компилирует в `Assets.car` (Liquid Glass на macOS 26, готовые
рендеры для macOS 15) и запасной `AppIcon.icns`;
подпись ad-hoc с entitlements hypervisor + disable-library-validation. Приложение можно
перенести в `/Applications`.

Запуск из Finder (без аргументов) берёт ядро, initramfs и слой из бандла, а диск SteamOS — из
Настройки → Дополнительно → Образ диска. По умолчанию:
`~/Library/Application Support/es.fxgam.steamac/steamos.img`, иначе `work/out/steamos.img`
репозитория (рядом с бандлом или там, где он был собран). Если диска нет — окно первого запуска:
**Новый диск…** (см. следующий раздел) или **Выбрать диск…** (образ используется на
месте и никогда не копируется; собирается и `scripts/build-image.sh`). Диск должен быть сырым GPT-диском
SteamOS с разделами этой разметки: архив восстановления Steam Deck или установщик Steam для macOS
отклоняется при выборе, а сохранённый неподходящий диск — до загрузки (STEAMAC-7Y/7Z). Если initramfs
гостя всё же падает (`steamac-init: FATAL …`), окно показывает ошибку, а не висит на 3%. Если диск нельзя
открыть или заблокировать (права, доступ к съёмным томам), лаунчер объясняет, что проверить в Finder →
Свойства → Общий доступ и права доступа и в «Конфиденциальность и безопасность», и пишет это в лог без
отчёта о сбое (STEAMAC-15). Консоль гостя и лог лаунчера в этом режиме
пишутся в `~/Library/Logs/es.fxgam.steamac/steamac-vm.log`, SIGUSR1-дампы кадра — туда же.
`./run.sh` и `work/out/steamac-vm` работают как раньше (настройки из окна действуют и для них,
если не заданы флагами).

Если образ лежит на внешнем диске, при первом запуске из Finder macOS спрашивает «FX Steam
Launcher хочет получить доступ к файлам на съёмном томе» — нужно разрешить (до ответа ВМ ждёт
на открытии диска). Подпись ad-hoc, поэтому после пересборки бандла macOS может спросить снова.

Один образ диска одновременно использует только одна ВМ: процесс ВМ держит эксклюзивную блокировку
(`flock`) на записываемом диске до выхода, и второй лаунчер (другая копия приложения, например сборка
из исходников рядом с `/Applications`, или `steamac-vm`) не запускается, а показывает «SteamOS уже
запущена», вместо того чтобы смонтировать те же файловые системы второй раз (это портит
`/home` и `/var`). Блокировка держится и после убитого лаунчера, пока гость ещё выключается.
Лаунчеры, собранные до блокировки, её не проверяют.

Если в `/home` при загрузке всё же есть ошибки (ВМ убита во время записи или диск открыли два старых
лаунчера без блокировки), SteamOS чинит его, а не останавливается на «Запуск служб SteamOS…»:
лаунчер добавляет `fsck.repair=yes` в командную строку ядра, и systemd-fsck запускает e2fsck с ответом
«да» на все вопросы, а не только с безопасными исправлениями preen. Файлы, которые e2fsck не смог
вернуть на место, оказываются в `/home/lost+found`.

## Языки

Интерфейс лаунчера — на английском, русском и упрощённом китайском и следует языку macOS (Системные
настройки → Основные → Язык и регион, в т. ч. отдельно для приложения в разделе «Приложения»). Журналы,
вывод командной строки, отчёты о сбоях и о проблемах остаются на английском. Фиксированные тексты этапов
Steam от агента гостя («Checking for Steam updates», …) показываются переведёнными
(`BootProgress.localizedGuestText`); прочий текст гостя (строки systemd, сама SteamOS) лаунчер не переводит.

Строки хранятся в String Catalog: `host/launcher/Localizable.xcstrings` (ключи — английский текст) и
`host/launcher/InfoPlist.xcstrings` (запросы разрешений). В коде литералы SwiftUI (`Text("…")`,
`Button("…")`) локализуются сами; любая другая строка интерфейса пишется как
`String(localized: "… \(value) …")` — одно предложение на ключ, аргументы интерполяцией, без склейки
из кусков, — а текст для журналов и CLI остаётся обычной английской строкой. `host/launcher/build.sh`
компилирует с `-emit-localized-strings`, синхронизирует извлечённые ключи в каталог (новые добавляются,
удалённые помечаются stale — каталог коммитится вместе с кодом), выводит непереведённые ключи и
несовпадения аргументов формата (`host/launcher/l10n.py check`) и компилирует каталоги в `<lang>.lproj`
рядом с `work/out/steamac-vm` и в `Contents/Resources` приложения. `dist.sh` не выпускает релиз с
неполным языком. Перевод без Xcode: `host/launcher/l10n.py export ru todo.json` — список недостающего,
`host/launcher/l10n.py import ru done.json` добавляет `{"ключ": "текст"}` или
`{"ключ": {"plural": {"one": …, "few": …, "many": …, "other": …}}}`; каталоги открываются и в Xcode.
Проверить язык, не меняя системный: `work/out/steamac-vm -AppleLanguages '(ru)' …`.

## Создание диска SteamOS без Docker (Creating the SteamOS disk without Docker)

Пользователю приложения Docker не нужен: диск создаёт сам лаунчер — окно первого запуска
**Новый диск…** или **Настройки → Дополнительно → Новый диск…** (ветка stable/rc,
размер home, место, пароль пользователя `steamos`; прогресс, Остановить и Создать). Доступны только stable
и rc: beta/preview/main могут быть подписаны ключом разработки Valve, которому лаунчер не доверяет.
Сохранённая неподдерживаемая ветка заменяется на stable с записью в журнал. То же без окна:

```sh
work/out/steamac-vm --create-disk ~/steamos.img [--branch stable] [--home-gib 64] [--password PW] [--keep-cache] [--accept-eula]
```

Ничего не скачивается, пока пользователь не принял условия Valve: «End User License Agreement for
SteamOS and Steam Client Back-Up Image» (тот же текст, что на странице образа Steam Frame,
`https://store.steampowered.com/steamos/download/?ver=steamframe`: только личное использование, без
распространения) и Steam Subscriber Agreement. В окне это флажок со ссылками на оба текста — без
него Создать недоступна; в командной строке — `--accept-eula`, без него `--create-disk` печатает
ссылки и завершается с кодом 2. Принятие (дата и URL соглашения) хранится в домене настроек и
действует, пока URL соглашения в коде (`SteamOSLicense.eulaURL`) не изменится.

Диск можно хранить на внешних томах APFS, Mac OS Extended и exFAT; рекомендуется APFS. FAT32/MS-DOS
отклоняется до скачивания из-за ограничения 4 ГиБ на файл (один временный rootfs занимает 10 ГиБ), как и
NTFS, сетевые файловые системы и неизвестные драйверы файловых систем (STEAMAC-8S: драйвер NTFS через час
скачивания отказал 92-гигабайтному диску с «File too large»); поздний отказ по размеру файла объясняется
пользователю и пишется в лог, но не отправляется в Sentry.
Тома только для чтения и папки без права записи тоже отклоняются. В отличие от APFS, exFAT не поддерживает разреженные файлы:
нужно место под полный выбранный размер диска и временный rootfs ещё до установки игр. Кеш скачивания там тоже занимает
намного больше своих ~4,4 ГБ данных: macOS хранит атрибут происхождения (provenance) каждого файла чанка в отдельном файле `._`,
а каждый файл и папка занимают целые кластеры (128 КиБ на диске 2 ТБ), всего около 28 ГБ. Лаунчер проверяет это место до
восстановления rootfs, а на exFAT удаляет кеш чанков перед выделением диска, если иначе тому не хватит места
(`--keep-cache` сохраняет кеш и требует места под оба).
Ожидаемые ошибки места хранения (существующий файл, занятый кеш, том только для чтения, отсутствие прав,
нехватка места, отключение диска, исчезновение папки диска или кеша во время создания или ошибка
ввода-вывода) записываются с подсказкой в журнал, но не отправляются
в Sentry, в том числе после начала создания. То же относится к сетевым сбоям метаданных/бандла
(нет сети, DNS, таймаут, разрыв соединения и отказ системной проверки TLS) и исчерпанным повторам desync,
включая таймаут при чтении тела HTTP-ответа чанка (STEAMAC-92). Если desync не может сохранить чанк в кеш
(`invalid argument` на кеше exFAT, STEAMAC-90/91), в лог пишется состояние сбойного шарда кеша (режим,
число записей и временных файлов, ошибки чтения).
Проверка сертификатов HTTPS никогда не отключается. Неожиданные ошибки и сбои проверки подписи бандла
по-прежнему отправляются с исходной диагностикой в деталях события. Если встроенный desync отсутствует,
нечитаем или не исполняем (STEAMAC-8K), окно объясняет, что установка неполная: переустановите приложение
из официального DMG в «Программы» и проверьте защитное ПО. Одно предупреждение на установку содержит
translocation, наличие и права desync, результат проверки подписи и имена и размеры файлов Resources
относительно бандла; абсолютный путь остаётся в локальном логе, окно отчёта о сбое не открывается.
Предупреждение также фиксирует, существуют ли ещё бандл, `Contents` и `Resources` (тип и errno): при
перемещении, удалении или замене приложения во время работы все три исчезают (STEAMAC-AE), поэтому
инструкция просит полностью закрыть FX Steam Launcher перед заменой или перемещением, а затем снова
открыть его из «Программы».
Лаунчер пишет в журнал тип файловой системы диска и кеша. Коллизия переименования чанка в кеше запускает
один повтор с одним потоком без кеша. При несовпадении хеша rootfs последовательное чтение отличает
неверные сведения о разреженных областях от повреждённых байтов. Во втором случае временный rootfs и кеш
чанков удаляются, затем загрузка повторяется один раз последовательно без кеша; оба слота диска очищаются.
Повторный сбой целостности отправляется в Sentry; диск не публикуется без совпадения с подписанным манифестом.
В отчёт попадают последовательный SHA-256 и первый блок в 1 МиБ, где повторное чтение источника отличается
от rootfs-A (смещение и хеши обоих блоков), чтобы отличить нестабильное чтение от ошибки копирования
(STEAMAC-9F/9H).
Создание диска сверяет прочитанную таблицу разделов с записанной — в приватном файле и после публикации
диска. Расхождение (STEAMAC-6J, exFAT) или пропажа восстановленного rootfs до выделения диска
(STEAMAC-68) по-прежнему отправляются, с идентификаторами файлов и различающимися полями GPT; окно
советует проверить накопитель «Первой помощью» Дисковой утилиты или выбрать другой.

Если не удаётся безопасно подключиться к Valve, окно объясняет, что могут мешать VPN, прокси или
сетевой фильтр: попробуйте отключить их или сменить сеть. Проверка обновлений даёт такой же совет
для GitHub. Технические детали сохраняются в журнале лаунчера. Для HTTPS используются стандартные
проверки сертификатов и настройки TLS macOS; закреплённый CA Valve ниже проверяет скачанный бандл,
а не HTTPS.

Ветка `rc` остаётся доступной, но Valve иногда подписывает её свежую сборку ключом разработки
`steamos-dev-images`, а не производственным CA. Такая сборка не принимается: лаунчер объясняет,
что подпись ключом разработки проверить нельзя, и предлагает выбрать `stable` или попробовать позже.
Этот ожидаемый отказ только записывается в журнал; остальные ошибки подписи по-прежнему отправляются в Sentry.

1. `https://steamdeck-atomupd.steamos.cloud/meta/holo/steamos/aarch64/vr/<ветка>.json` → свежий
   кандидат (`update_path`, `chunks_store_path`).
2. Скачивается `.raucb` (~2 МБ); CMS-подпись проверяется Security.framework только против
   закреплённого CA Valve `CN=steamdeck-images` (`scripts/keys/steamdeck-images.pem`, SHA-256 отпечаток
   зашит в код); системное хранилище доверия не используется. Свой читатель squashfs (zstd из
   закреплённого релиза zstd, `fetch-zstd.sh`) достаёт `manifest.raucm` и `rootfs.img.caibx`;
   проверяются `compatible=steamos-aarch64`, версия и размер слота.
3. Официальный desync (`fetch-desync.sh`, версия и sha256 закреплены) собирает 10-гигабайтный
   `rootfs.img` из хранилищ чанков Valve (~4,4 ГБ данных); кеш чанков — `desync/` в
   `~/Library/Caches/es.fxgam.steamac` для диска на томе домашней папки, иначе в `<диск>.cache`
   рядом с диском (внешнему диску тогда не нужно место на внутреннем; после успеха папка удаляется).
   Поэтому Остановить/Создать (или повтор команды после Ctrl+C) продолжает с места остановки; готовый
   `<диск>.rootfs-tmp`, оставшийся от попытки, сорвавшейся позже, сначала удаляется (desync его не
   использует, а место он занял бы дважды). Одновременно — одно создание на кеш: второе (другое окно или
   `--create-disk`) останавливается с «с кэшем загрузки … уже создаётся другой диск SteamOS: дождитесь завершения или отмените создание» (`flock` на
   `creation.lock` в папке кеша), а не делит кеш чанков и временные файлы.
4. Разреженный файл диска: защитный MBR + GPT (основная и резервная, CRC32) ровно с именами,
   порядком, типами, размерами и выравниванием `scripts/steps/40-disk.sh`, случайные PARTUUID.
   За один проход `rootfs.img` хешируется (sha256 должен совпасть с подписанным манифестом) и
   ненулевые блоки по 16 КиБ пишутся в rootfs-A и rootfs-B; остальные разделы — нули. Диск
   появляется под своим именем только после всех проверок. Существующие файлы не перезаписываются;
   на exFAT, где нет атомарного эксклюзивного переименования, лаунчер проверяет путь под блокировкой
   создания и затем переименовывает файл. Не создавайте и не перемещайте другой файл на этот путь
   сторонней программой во время создания: относительно неё проверка и переименование не атомарны.
5. Рядом кладётся `<диск без .img>.provision.img` — cpio newc с `provision.env` (сборка, PARTUUID,
   хеш пароля SHA-512 crypt, machine-id) и `rootfs.caibx` (формат — «Payload v1» в контракте
   провижининга). Пока этот файл есть, лаунчер подключает его только для чтения (vdc) и добавляет
   `steamac.provision=1`: initramfs форматирует esp/efi-X/var-X/home, делает fsid rootfs-B
   уникальным, пишет partsets/bootconf/bootenv/var и сообщает `provision done` — после этого лаунчер
   удаляет payload, следующие загрузки идут без него.

Место на томах с разреженными файлами: ~20 ГБ на томе диска при создании (потом ~9 ГБ), плюс ~6 ГБ кеша.
desync на macOS заранее выделяет все 10 ГиБ временного rootfs даже на APFS; разреженными остаются только два слота.
Проверка места учитывает это выделение и запас (всего ~27 ГБ для SteamOS 20261007). Кеш удаляется после успеха,
если не указан `--keep-cache`. Проверки: `work/out/steamac-vm --selftest-provision` — GPT против
диска из Docker-сборки (`work/out/steamos.img` открывается только на чтение; `--reference-disk IMG`),
CMS/squashfs против кеша `work/cache/rootfs`, cpio, SHA-512 crypt.
Самотест также проверяет сетевые сообщения, отсутствие отчётов об ожидаемых сетевых и файловых сбоях,
отправку неожиданных ошибок и копирование разреженного rootfs в оба слота с обходом областей и последовательно.
Для проверки настоящего сбоя TLS без отправки событий задайте
`STEAMAC_PROVISION_TEST_TLS_URL=https://localhost:PORT/` с адресом локального сервера
с недоверенным сертификатом при запуске `--selftest-provision`: он выведет сообщение и проверит отсутствие отчёта.

## Клиент Steam (Steam client)

Какой клиент Steam запускает SteamOS, выбирается в лаунчере: окно первого запуска, окно
**Создать диск SteamOS** и **Настройки → Дополнительно → Клиент Steam** (применяется при следующем запуске, «Перезапустить ВМ
для применения»), для одного запуска — `--steam-client frame|deck|deckbeta`. Лаунчер передаёт выбор при
каждой загрузке в cmdline ядра `steamac.steam_client=…`; его читает `/usr/lib/steamac/steam-client`
из слоя при каждом старте Steam. Сервис Steam остаётся стоковым из SteamOS (`steam.service`), слой
добавляет к нему только drop-in `steam.service.d/50-steamac.conf`; `steam-client` перед стартом
копирует стоковый `/usr/share/deckard/RUNSTEAM.sh` в `~/.local/share/Steam/` — без изменений для
клиента Frame с запомненным аккаунтом, а в режимах `deck`/ветки/входа удаляет из копии только строки
аргументов `-deckard` и `-vrgamepadui`. Файлы Valve в слой не входят.

| Вариант | Что это | Плюсы и минусы |
|---|---|---|
| **Клиент Steam Deck** (`deck`, по умолчанию) | публичный ARM64-клиент Steam Deck, ветка `steamdeck_stable` (та же сборка, что публичный `steam_client_linuxarm64`; официально для ARM не объявлен) | обычный вход с QR-кодом на экране; публичная ветка клиента, а не внутренняя бета; **Proton Experimental (ARM64)** — отдельный вариант совместимости, не x86-64 **Proton Experimental** |
| **Клиент Steam Deck (бета)** (`deckbeta`) | ветка `steamdeck_publicbeta` | как `deck`, но бета |
| **Клиент Steam Frame** (`frame`) | бета-клиент Valve для Steam Frame (`linux_arm64_beta_<hash>`, флаги `-deckard -vrgamepadui`) — как в образе | клиент, который идёт в образе; внутренняя бета ещё не вышедшего устройства; вход — через режим входа (ниже) |

Смена варианта при следующем старте Steam скачивает другой клиент (до ~1 ГБ, прогресс в оверлее
загрузки); обратно на Frame загрузчик Steam переключается сам по флагу `-deckard`. Ручной
`/etc/steamac/steam-client-branch` внутри SteamOS (любая ветка клиента) по-прежнему работает, когда
выбран `frame` (или лаунчер не передаёт параметр — старые версии, свой `--cmdline`); выбор `deck` /
`deckbeta` в лаунчере важнее файла.

## Vulkan-драйвер (Vulkan driver)

Vulkan-драйвер хоста за Venus выбирается в **Настройки → Дополнительно → Драйвер Vulkan** (при следующем
запуске) или на один запуск флагом `--vulkan-driver moltenvk|kosmickrisp`. По умолчанию — KosmicKrisp,
если он есть у Mac и сборки (macOS 26+, сборка на macOS 26+), иначе MoltenVK; драйвер, выбранный в
Настройки, сохраняется. virglrenderer открывает
драйвер во время работы (без Vulkan-загрузчика): перед стартом ВМ лаунчер ставит `VKR_VULKAN_DRIVER`
в `@rpath/libMoltenVK.dylib` или `@rpath/libvulkan_kosmickrisp.dylib`. Оверлей загрузки показывает
драйвер («Venus → KosmicKrisp»); в отчётах о сбоях есть `vulkan_driver` и ревизия патчей драйвера.

До инициализации Metal лаунчер проверяет доступность для записи кеша модулей компилятора
(`DARWIN_USER_CACHE_DIR/<bundle id>/com.apple.metalfe`, включая папки хешей и существующие `.pcm`).
Если запись блокируют права, ACL или флаг immutable, лаунчер записывает проблемный путь в журнал
и перенаправляет Metal в `~/Library/Caches/es.fxgam.steamac/metal-compiler`.
Старый кеш не удаляется, его права не меняются. Используется необязательный SPI Metal для пути кеша;
если он недоступен или новый кеш тоже недоступен для записи, это фиксируется в журнале, а ошибки
компиляции шейдеров по-прежнему отправляются в отчётах. `work/out/steamac-vm --selftest-metal-cache`
воспроизводит `monolithic_metal.pcm: Operation not permitted` в отдельном временном immutable-кеше
и проверяет настоящую компиляцию Metal с новым кешем (без ВМ и событий Sentry). Выбор делается только
до инициализации Metal: кеш, ставший недоступным позже, в работающем процессе перенаправить нельзя,
поэтому отчёты содержат решение при запуске (тег `metal_cache`) и метаданные (только чтение) пути
`monolithic_metal.pcm`, на котором произошёл сбой (STEAMAC-7W). MoltenVK не поддерживает конвейеры с тесселяцией и
геометрическим шейдером одновременно: они завершаются `VK_ERROR_FEATURE_NOT_PRESENT`, а не компилируются
с недопустимой привязкой буфера (STEAMAC-83).

Смена драйвера меняет идентичность драйвера Venus (UUID кэша конвейеров): Steam и игры заново
собирают кэши шейдеров. Конвейер, который драйвер хоста не смог собрать, остаётся заглушкой в
virglrenderer: его draw и dispatch отбрасываются, `VK_NULL_HANDLE` до драйвера не доходит.

Драйверы хоста отклоняют входные данные Vulkan, на которых assert Metal завершил бы всю ВМ, и пишут
аргументы Vulkan в лог. KosmicKrisp: view изображения с пустым или выходящим за границы диапазоном
слоёв либо между цветовыми форматами разного размера блока завершается `VK_ERROR_FORMAT_NOT_SUPPORTED`
(STEAMAC-62/3); дескриптор, который шейдер использует, а layout конвейера не содержит, читается нулём,
запись в него отбрасывается (STEAMAC-6H); копирование изображений через промежуточный буфер не
выходит за границы mip-уровня и учитывает все срезы объёма (STEAMAC-5E/5F); LINEAR-изображения с
mip-уровнями, слоями, глубиной или сэмплами сверх того, что сообщает запрос формата, отклоняются в
`vkCreateImage` (STEAMAC-3F/6Y); у закэшированного предкомпилированного NIR-шейдера хранится BLAKE3,
который проверяется до десериализации: повреждённая запись — промах кэша, а не падение. У падений
STEAMAC-6M/6K/7J/7H/7P в `vkCreateComputePipelines` была другая причина: сериализатор NIR в Mesa хранил
индексы источников в 20 битах, и у шейдеров с более чем 2^20 объектами после десериализации источники
указывали на посторонние объекты; большие индексы теперь пишутся отдельным словом
(`host/kosmickrisp/test/nir_object_ids.c` при сборке KosmicKrisp проверяет шейдер с более чем миллионом defs).
Ветвления глубже 128 уровней выводятся как соседние блоки с сохранёнными условиями, потому что Metal не
принимает исходник с вложенностью скобок больше 256 (отчёт STEAMAC-G; `sentry-g-brackets.sh` проверяет на
GPU лестницу из 320 расходящихся ветвей). Для воспроизводимого зависания KosmicKrisp `MESA_KK_DEBUG=syncs,cbs`,
заданный при запуске лаунчера на macOS (а не как аргумент игры), трассирует синхронизацию очереди и каждое
ожидание CPU дольше секунды (STEAMAC-94).
Копирование буфера с NULL вместо исходного или целевого буфера пропускается с одним предупреждением,
не роняя процесс ВМ (Dota 2, STEAMAC-9S/9T; `host/kosmickrisp/test/copy-buffer-null.py`).
Запасной барьер Mesa на macOS мог навсегда подвесить `util_queue_finish` при закрытии устройства
(дисковый кэш шейдеров); `host/kosmickrisp/test/util_queue_finish.c` запускается при сборке KosmicKrisp.
MoltenVK: конвейер с блендингом вложения, которое Metal не умеет блендить (R32_UINT), не создаётся
(STEAMAC-3A); вспомогательные буферы вершинной стадии упаковываются в 31 слот буферов Metal (STEAMAC-67);
работают полные 32-битные ID specialization constants (STEAMAC-6A); optimal-изображение в импортированной
памяти хоста получает placement heap, и 2D-виды 3D-изображения как вложения рендера больше не обращаются к
отсутствующему heap (STEAMAC-76/77); при сбое конвейера в журнал попадают небольшие шейдеры целиком,
дескрипторы Metal, состояние блендинга и индексы выходов фрагментного шейдера (STEAMAC-41/75).
Для вложения, у фрагментного шейдера которого нет второго выхода, факторы dual-source блендинга берут
для него ноль: Vulkan оставляет значение неопределённым, а Metal такой конвейер отвергал (STEAMAC-75); на M1
перспективная проекция с квалификатором sample интерполируется в `get_sample_position(sample_id)`, что
обходит отсутствующий в Metal интринсик `llvm.agx2.sample.itrproj` (STEAMAC-8J). SPIRV-Cross исправляет
ошибки MSL из STEAMAC-33/6D/6E/5M/5K/2N/5C/6V, сохраняет второй индекс dual-source блендинга при упаковке
выходов (STEAMAC-75), явные Location членов интерфейсных блоков с пропусками (Location 0 и 2 становились
`locn0`/`locn1`) и объявляет `locations` в полезной нагрузке object-шейдера как `uint[32][4]` (та же
раскладка): компилятор Apple падал на частичных записях в `uint4 locations[32]`, что выглядело как
внутренняя ошибка или прерванное XPC-соединение (STEAMAC-41/R); отчёты о прерванном сервисе компилятора
содержат давление памяти и swap хоста (STEAMAC-3X). Члены `vec3` в массивах Workgroup (общей памяти)
хранятся упакованными, как их размер считает правило выравнивания Vulkan: массиву из 968 `{float; vec3;
float}` нужно 19360 байт, а не 46464 > 32768 по раскладке Metal (STEAMAC-57). Вершинный выход уже
фрагментного входа в той же Location (float3 → float4) расширяется до ширины входа; отсутствующие varyings
и разные числовые типы по-прежнему не поддерживаются (STEAMAC-2M/88).
Шейдерная функция с именем `rgb9e5` переименовывается, чтобы не конфликтовать с пиксельным типом Metal
`rgb9e5` (STEAMAC-A9), а геометрическая/mesh-стадия, записывающая только `ClipDistance`, записывает также
копию `user(clip0)`, которую читает фрагментный шейдер (STEAMAC-A2).
`host/moltenvk/repro/sentry-msl.sh` компилирует
каждый восстановленный шейдер. wmtr (DXMT) отклоняет только мусорные и освобождённые хэндлы объектов,
закрывает энкодеры, оставленные игрой открытыми, когда её контекст уходит (в том числе при более чем
65 536 живых объектах, STEAMAC-70), и не создаёт конвейер без вершинной функции (STEAMAC-6S/6Z);
`wmtr/tests/wmtr_dxmt_test.m` прогоняет собственные списки команд DXMT через поставляемый исполнитель на GPU.

**Разрешить DXMT (D3D11 через Metal на Mac), экспериментально.** Настройки → Дополнительно →
**Разрешить DXMT (D3D11 через Metal на Mac)** по умолчанию выключено и действует со следующего
запуска (`--wmtr-lib PATH` или `--no-wmtr` на один запуск). В приложение вложен `libwmtr_host.dylib`,
в гостевой слой — DXMT:
`{d3d11,dxgi,d3d10core,winemetal}.dll` и `winemetal.so`. Если macOS не может выдать Metal drawable
(например, слой нулевого размера или таймаут drawable), DXMT пропускает кадр вместо показа `nil`, на
котором Metal срабатывал assert и ВМ завершалась (STEAMAC-98); это пишется в лог с ограничением, и
отрисовка продолжается со следующего drawable. При включении лаунчер даёт гостю контекст
virtio-gpu wmtr из libkrun (патч 0018, capset 30) и загружает ВМ с `steamac.gfx=dxmt`.
Гостевой `steam-gfx-path` подменяет библиотеки каждого установленного x86-64 Proton на DXMT и
следит за установками и обновлениями Proton; после выключения ВМ загружается с `steamac.gfx=vulkan`, и
исходные файлы Proton восстанавливаются. С необязательным ARM64EC-набором `steam-dxmt-arm64ec` готовит из установленного **Proton 11.0
(ARM64)** отдельный инструмент совместимости **SteamMac DXMT (ARM64EC)**. В нём DLL ARM64X из DXMT и
`winemetal.so` в формате AArch64 ELF: Wine и DXMT работают нативно, а FEX транслирует только
x86-64-код игры. Тонкий инструмент — это symlink'и на установленный Proton, около 13 МБ файлов
DXMT и отдельные префиксы-шаблоны и исправляемые записи, а не полная копия на 1,9 ГБ.
Исходные файлы Proton не меняются, его обновления сразу видны по ссылкам.
Proton берёт свой каталог из пути, по которому его запустили, и при каждом запуске копирует свой
набор DXVK в префикс: `d3d11`/`dxgi`/`d3d10core` из DXMT на этом месте в инструменте попадают в
префикс, а игра, возвращённая на инструмент Steam по умолчанию, при следующем запуске снова получает
DXVK. Сам Wine остаётся стоковым; `winemetal` берётся из инструмента через `WINEDLLPATH`, а точка входа
`run` держит запись `winemetal.dll` в префиксе игры. Инструмент пересобирается перед стартом Steam,
когда меняется Proton или набор; пока игра использует инструмент, обновление откладывается.
Удалённый или неподдерживаемый Proton делает управляемый инструмент недоступным: назначения
возвращаются к запасному пути, а не к битым или несовместимым ссылкам. Исправления SteamPipe для
пустых каталогов и прав только для чтения применяются к отдельным префиксам-шаблонам и исправляемым
записям (остальные файлы копируются лишь при необходимости исправить права), даже до первого
запуска стокового Proton.
Вложенный каталог `tool/` не подпускает к нему прежний x86-64-установщик.

Перед стартом Steam `steam-compat-default` даёт **только играм, в профиле которых выбран DXMT**,
назначение на нативный инструмент, если он есть, иначе на **Proton 10.0**, с приоритетом 250, и
только при загрузке с DXMT. Прежний набор только для x86-64 не может инициализировать winemetal под
ARM64EC Wine: нужны и нативные PE DLL, и нативная Unix-библиотека.
Подходят установленные Windows-игры
(по `libraryfolders.vdf` и `appcache/appinfo.vdf`: тип game/demo/application, oslist с windows без
linux), если пользователь не выбрал свой инструмент. Все остальные сохраняют инструмент Steam
по умолчанию — **Proton 11.0 ARM64**, DXVK/vkd3d-proton на Venus. Прежнее назначение Proton 10.0
всем играм снимается при первом старте Steam; дальнейшие изменения профиля и новые установки игр
применяются при следующем старте Steam. Пользовательские правки в Steam остаются нетронутыми.
Дело не только в DLL: некоторые игры падают под x86-64 Proton 10.0 + FEX независимо от библиотек.
Например, у Stellar Blade Demo (3564860) рекурсия SEH заканчивается
`virtual_setup_exception stack overflow`, а на Proton 11.0 ARM64 игра работает.
Для запасного пути Steam скачивает Proton 10.0 (x86-64, под FEX в Steam Linux Runtime 3.0) при первом запуске игры с
DXMT, и `steam-gfx-path --watch` кладёт в него DXMT. Сборкам **x86-64** Proton Experimental и
Proton 11.0 нужен x86-64 Steam Linux Runtime 4.0 (`SteamLinuxRuntime_4`, приложение 4183110).
Не путайте их с **Proton Experimental (ARM64)** и **Proton 11.0 (ARM64)**: им нужен отдельный ARM64 runtime
(`SteamLinuxRuntime_4-arm64`, приложение 4185400), который Steam устанавливает на ARM64.
В **Свойствах → Совместимость** игры выбирайте инструмент с явным **(ARM64)** в конце названия;
клиент Steam Deck тоже предлагает ARM64 Experimental, переходить на Frame ради него не нужно.
Общая запись («0») не используется: Steam применяет приоритетный wildcard и к своим инструментам
и так опустошил инструмент FEX. Выключение «Разрешить DXMT» удаляет назначения скрипта.
D3D12 на Proton 10.0 выполняет часть Wine под FEX, а не ARM64EC, что стоит процессорного времени.

Вызовы winemetal из DXMT идут
через virtio-gpu к исполнителю **внутри процесса ВМ на Mac**, который выводит `CAMetalLayer` во

собственный курсор игры с размером как в gamescope. Отслеживание курсора разрешает хост, и оно нужно
только DXMT: лишь когда фокус игры допускает оверлей и настоящий слой wmtr присоединён и видим,
а не просто включено «Разрешить DXMT» (см. «Курсор на пути DXMT» в «Как это устроено»).
D3D12 (vkd3d-proton) и нативный Vulkan остаются на Venus; этот путь — **только для D3D11/D3D10**,
не D3D9. В DXMT ещё есть пробелы совместимости, в том числе **нет stream output**;
при первом запуске ожидайте компиляцию шейдеров и рывки: кэш Vulkan Steam не покрывает Metal.

**Безопасность: пока это включено, гостевые программы могут выполнять код на Mac с правами
вашего пользователя.** Исполнитель в процессе ВМ и протокол DXMT с сырыми адресами хоста —
не граница безопасности ВМ. Поэтому путь выключен по умолчанию и экспериментален; сбой
исполнителя также может остановить ВМ. Включайте только для гостевых программ, которым доверяете.

Перед запуском ВМ лаунчер ставит `STEAMAC_WMTR=1`, `STEAMAC_WMTR_LIB` (переопределение
**Библиотека-исполнитель**, иначе `@rpath/libwmtr_host.dylib` из Frameworks приложения или
`work/out/host/lib`) и `WMTR_PRESENT=overlay`; при выключении убирает все три. Отсутствующая/
незагружаемая библиотека или отсутствие `wmtr_host_abi_version` выключает путь на эту загрузку
(в логе и красным в Настройках; явный `--wmtr-lib` завершает лаунчер с причиной); другую
версию ABI отвергает libkrun. Отчёты о проблемах и сбоях содержат `wmtr on|off`.

**Сборка DXMT.** На macOS с Apple silicon установите Metal toolchain из Xcode
(`xcodebuild -downloadComponent MetalToolchain`), Rosetta (`softwareupdate --install-rosetta`
для x86-64 инструмента сборки Wine), Homebrew и Docker/OrbStack с поддержкой `linux/amd64`
для шага client. Скрипт ставит `meson ninja cmake pkgconf zstd`. Без Metal toolchain можно
указать `DXMT_PREBUILT_METAL`: каталог с `dxmt_command.metallib` и
`air_{msad,samplepos,tessellation}.air`, собранными из тех же закреплённых исходников.

```sh
host/dxmt/build.sh fetch llvm native host pe client payload  # шаги по умолчанию, по порядку
host/dxmt/build.sh pe-arm64ec client-arm64 payload-arm64ec    # добавить нативную поддержку Proton 11
scripts/build-image.sh layer                               # вложить гостевые библиотеки
host/launcher/build.sh                                     # вложить исполнитель и обновлённый слой
```

`fetch` проверяет закреплённые архивы DXMT/DirectX headers и применяет `host/dxmt/patches`;
`llvm` собирает статический LLVM 15.0.7 (около 10 минут на M2, переиспользуется при том же pin).
`native` собирает airconv в `work/build/dxmt-native`; `host` собирает/тестирует/устанавливает
исполнитель в `work/out/host/lib/libwmtr_host.dylib`. `pe` кросс-компилирует четыре DLL в
`work/out/dxmt-pe`; `client` собирает/тестирует `wmtr/build/x86_64-linux/winemetal.so` в Docker;
`payload` размещает `work/out/dxmt/{x86_64-windows,x86_64-unix}` для
`/usr/lib/steamac/dxmt/` гостевого слоя. Шаги можно запускать отдельно; `host/dxmt/build.sh`
без аргументов выполняет шаги x86-64 по умолчанию.
Три необязательных шага ARM64EC используют закреплённые инструменты сборки Wine 11.2 и
`build-arm64ec.txt` из DXMT, собирают и тестируют Unix-клиент в нативном ARM64-контейнере и
размещают `work/out/dxmt/{aarch64-windows,aarch64-unix}` рядом с x86-64-набором. Исполнитель на
хосте общий для обеих архитектур. Проверки упаковки и назначения: `python3
scripts/test/steam-dxmt-arm64ec.py`, `python3 scripts/test/steam-compat-default.py` и `bash
scripts/test/steam-gfx-path.sh`. Smoke-тест создания устройства и чтения буфера —
`wmtr/tests/d3d11_device_test.c`; запускайте его x86-64-сборку под нативным инструментом DXMT при
загрузке с включённым исполнителем wmtr.

Благодарности: [StonkGuy](https://github.com/StonkGuy/steamac) — ремотинг wmtr и интеграция;
[DXMT от 3Shain (Feifan He)](https://github.com/3Shain/dxmt) — D3D11/D3D10 на Metal.
Заимствованные исправления в `host/dxmt/patches` сохраняют авторов: David Grinberg, osy,
Holly Hamilton, SteveTanSaMa, hanzpo, Mybono, NerRobDog, 时雨 и Jakey-Jakey
(подробности в `STEAMAC-README.md` пропатченного DXMT).

Каждое host-visible выделение памяти гостя — POSIX shm, чьи файловые дескрипторы остаются открытыми
в процессе ВМ (около четырёх на отображённое выделение), а запуск из Finder начинается с мягкого
лимита в 256 дескрипторов: после нескольких десятков таких выделений игры теряли GPU-контекст
(STEAMAC-G, Left 4 Dead 2). Процесс ВМ при старте поднимает мягкий лимит до `kern.maxfilesperproc`
(в логе «file descriptors: soft limit 256 → N»); virglrenderer пишет errno неудавшейся операции с
shm или дескриптором («… failed: Too many open files (RLIMIT_NOFILE 256)»).

Проверки без ВМ: `host/kosmickrisp/build.sh` гоняет `host/moltenvk/probe` и repro
(`REPRO_DRIVER=kosmickrisp host/moltenvk/repro/run.sh <dylib>`, через Khronos-загрузчик, только для
тестов) на собранном драйвере; `host/virglrenderer/build.sh` гоняет `venus_check` с каждым
установленным драйвером.

## Вход в Steam (Signing in)

Экран входа клиента Steam Frame рассчитан на шлем: «Tap to confirm» связывается с телефоном по
Bluetooth LE, «Scan QR code» открывает VR-окно — в ВМ оба не работают (остаётся только пароль).
Поэтому с клиентом Steam Frame, пока в `config/loginusers.vdf` нет запомненного аккаунта (новый
диск, выход из аккаунта, вход без «Remember me»), `steam-client` запускает Steam без `-deckard`/`-vrgamepadui`: загрузчик сам
переключается на публичный ARM64-клиент Steam Deck (`steamdeck_stable`), и вход показывает
QR-код на экране (Steam Mobile App → Steam Guard → сканировать) рядом с формой пароля. После входа
с «Remember me» Steam один раз перезапускается и возвращается к клиенту Steam Frame (каждая смена
клиента — загрузка до ~1 ГБ, прогресс виден в оверлее загрузки). Без доступа к
`client-update.steamstatic.com` режим входа не включается.

Строки `RecvMsgClientLogOnResponse() : 'Try another CM'` в `connection_log.txt` на экране входа —
норма: сервер CM разрывает соединение без входа в аккаунт через ~60 с, клиент переподключается.

## Дистрибутив (DMG)

`host/launcher/dist.sh` делает из собранного `work/out/FX Steam Launcher.app` то, что выкладывается
для скачивания: `work/out/dist/FX-Steam-Launcher-<версия>.dmg` (приложение + ссылка на
`/Applications`). Копия бандла без ключа `SteamacBuildOut` (путь к этому дереву сборки)
переподписывается Developer ID с hardened runtime и secure timestamp изнутри наружу: сначала все
отдельные вложенные Mach-O (`Frameworks/*.dylib`, вспомогательные программы в `Resources`, `Autoupdate`
из Sparkle), затем вложенные бандлы от самых глубоких (`Updater.app` из Sparkle, `Sparkle.framework`),
затем бандл с
`steamac-vm.entitlements` (hypervisor, disable-library-validation и audio-input — без него hardened
runtime молча запрещает микрофон). Приложение нотаризуется и стейплится, затем DMG подписывается,
нотаризуется и стейплится — Gatekeeper пропускает его и офлайн (остаётся обычный вопрос
«загружено из интернета» при первом запуске).

```sh
host/launcher/build.sh      # свежий бандл
host/launcher/dist.sh       # подпись, нотаризация, DMG
```

Один раз нужен профиль notarytool в связке ключей:
`xcrun notarytool store-credentials steamac-notary --apple-id <Apple ID> --team-id V25VKGTW55
--password <app-specific password>`. Переменные: `STEAMAC_SIGN_IDENTITY` (по умолчанию
единственная «Developer ID Application» в связке), `NOTARY_PROFILE` (по умолчанию `steamac-notary`);
`--no-notarize` — только подпись, для локальной проверки (скачанную копию Gatekeeper не пустит).

Лицензии: `bundle.sh` кладёт в `Contents/Resources/licenses` все тексты лицензий сторонних
компонентов бандла и индекс `THIRD-PARTY-NOTICES.txt` (компонент, версия, SPDX, где лежит в бандле,
исходники; собирает `host/launcher/licenses.sh` в `work/out/licenses`, в том числе крейты libkrun и
модули Go из gvproxy/desync), плюс `LICENSE` и `NOTICE` проекта в `licenses/steamac/`. `dist.sh`
вызывает `scripts/gpl-sources.sh` и рядом с DMG кладёт
`work/out/dist/FX-Steam-Launcher-<версия>-gpl-sources.tar` — полный исходный код GPL-компонентов
(ядро с патчами и конфигом, busybox из Debian-снапшота, dosfstools, e2fsprogs, btrfs-progs, скрипты
сборки, `README.txt`); его прикладывают к релизу на GitHub вместе с DMG. Для старого релиза:
`scripts/gpl-sources.sh v1.2`.

Обновления в приложении ([Проверка обновлений](#проверка-обновлений)): `dist.sh` добавляет `SUFeedURL`
(`SPARKLE_FEED_URL`, по умолчанию `https://fxgl.github.io/steamac/appcast.xml`), `SUPublicEDKey`
(`SPARKLE_PUBLIC_KEY`, по умолчанию ключ релизов fxgl `ML1BKHcTTwKlVSLtTdMvyk7Fhwg35VN1nUp+o4fezt8=`,
зафиксирован в `dist.sh`: установленные копии принимают только подписанные им обновления),
`SUVerifyUpdateBeforeExtraction` и `SURequireSignedFeed`; нотаризованная сборка падает, если в связке
ключей нет закрытой половины этого ключа (`generate_keys -p` печатает открытую). Пара ключей EdDSA создана
один раз:
`host/launcher/.build/artifacts/sparkle/Sparkle/bin/generate_keys` (инструменты Sparkle приходят с
пакетом SwiftPM той же версии, что и встроенный фреймворк); закрытый ключ остаётся в связке ключей входа,
никогда не в репозитории и не в CI. Сохраните его копию офлайн (`generate_keys -x <файл>`;
`generate_keys -f <файл>` импортирует на другом Mac): без него установленные копии больше не получат
ни одного обновления. `build.sh` ставит `CFBundleVersion` равным `CFBundleShortVersionString` (по нему
Sparkle сравнивает версии). Релиз — именно в таком порядке (фид не должен ссылаться на ещё не
загруженные файлы):

```sh
host/launcher/dist.sh
gh release create v<версия> work/out/dist/FX-Steam-Launcher-<версия>.dmg \
    work/out/dist/FX-Steam-Launcher-<версия>-gpl-sources.tar --notes-file <notes.md>
host/launcher/appcast.sh    # docs/appcast.xml, дельта-обновления — к релизу
git commit -m "appcast: <версия>" docs/appcast.xml && git push    # GitHub Pages публикует фид
```

`appcast.sh` проверяет, что DMG в релизе — локальный (тот же размер), и запускает `generate_appcast`
из Sparkle на `work/out/updates` (архивы прежних версий; фид берётся из `docs/appcast.xml`): новая
запись с подписью EdDSA для DMG, минимальной macOS из `LSMinimumSystemVersion`, описанием релиза с GitHub
(Markdown, встроено) и адресом загрузки в этом релизе; дельта-обновления от до 3 прежних версий, чьи
DMG лежат в `work/out/updates` (ядро и большинство вспомогательных программ меняются редко), без пробелов
в имени (GitHub переименовывает такие файлы) и загруженные в релиз; подпись всего фида. Остальные
аргументы уходят в `generate_appcast`, например `--phased-rollout-interval 86400` (обновление доходит до
пользователей за 7 дней) или `--critical-update-version ''`. Не правьте `docs/appcast.xml` руками: подпись
покрывает весь файл. Локальная проверка от начала до конца: `dist.sh --no-notarize` с
`SPARKLE_FEED_URL=http://127.0.0.1:8765/appcast.xml` и `SPARKLE_PUBLIC_KEY=<тестовый ключ>` для двух
версий, после каждой `SPARKLE_KEY_FILE=<тестовый закрытый ключ> host/launcher/appcast.sh --local
http://127.0.0.1:8765`, и `python3 -m http.server 8765` в `work/out/updates-local`.

## Отчёты о сбоях (Sentry)

Лаунчер отправляет отчёты о сбоях и немногие ошибки на собственный сервер Sentry разработчиков
(`sentry.fxgam.es`, SDK sentry-cocoa 9.30.0 через SwiftPM). Включено по умолчанию; выключается
галочкой **Отправлять отчёты о сбоях и диагностические данные** — в «Настройки → Основные», в окне первого запуска и в
окне Создать диск SteamOS (ссылка «Что отправляется» показывает список ниже). Выключено — SDK вообще не
запускается, сетевых соединений нет (уже сохранённые отчёты остаются на диске и не отправляются).
На один запуск: `--no-crash-reports` или `STEAMAC_SENTRY=0`.

Что отправляется:

- падения процесса-супервизора и процесса ВМ (сигнал/abort, необработанные исключения): причина,
  стеки потоков, список загруженных библиотек. Сюда попадают assert'ы Metal/MoltenVK, abort'ы
  libkrun/virglrenderer и паники Rust, вышедшие через C API libkrun. Отчёт о падении процесса ВМ
  уходит при следующем запуске ВМ. Необработанное исключение Objective-C группируется по его причине
  (сообщение и стек первого выброса из stderr), а не под `CPPExceptionTerminate` (STEAMAC-58);
- немногие ошибки (не чаще раза на отпечаток за процесс, общий лимит, повтор того же отпечатка — не
  раньше чем через сутки, для ошибок компиляции шейдеров — 30 дней): гостевой GPU-контекст стал
  фатальным/потеря устройства (vkr «fatal decoder state», «device lost»), ошибки компиляции
  пайплайнов MoltenVK (`[mvk-error] … compile failed`; если MoltenVK напечатал исходник MSL
  (`[mvk-msl] …`: первые 40 строк и строки вокруг ошибки) — он уходит в extra `msl_source`, не в
  breadcrumbs; полный шейдер с ошибкой, до 256 КиБ и после очистки, прикладывается как файл `.metal`,
  не более двух разных шейдеров за процесс, с дедупликацией по хешу содержимого (STEAMAC-AD); строка vkr
  «pipeline … creation failed on host» — только breadcrumb),
  паника Rust в libkrun (`thread … panicked at`), провал первичной настройки диска (`provision
  failed`), провал создания диска, неожиданный выход ВМ (ненулевой код или сигнал, если выключение не
  запрошено пользователем), «SteamOS не отвечает…» индикатора простоя. При падении процесса ВМ отчёт
  супервизора дополняется собственным отчётом macOS о нём (`~/Library/Logs/DiagnosticReports/steamac-vm-*.ips`,
  по pid): место падения в заголовке и теге `crash_site` (отчёты группируются по нему), а в extra
  `macos_crash_report` — исключение, строки Application Specific Information (сообщение libmalloc при
  ловушке порчи кучи) и первые 16 кадров упавшего потока (имена библиотек и символов);
  Отчёты «SteamOS не отвечает…» включают `stall_history`: до 32 секундных отсчётов счётчиков GPU,
  возраста heartbeat, uptime/нагрузки гостя, процессорного времени процесса и интервала опроса на
  хосте, даже без статистики производительности (STEAMAC-8). Пропажа heartbeat агента сама по себе
  не доказывает зависание всей гостевой системы или GPU. Снимки активности GPU, памяти ВМ и потоков
  хоста ограничены по отдельности; состояния потоков и оценки CPU — это улики, а не стеки вызовов и не
  доказательство взаимоблокировки GPU. История также содержит активность приложения, ключевое окно и
  видимость/перекрытие окна. «Работа продолжается» значит, что heartbeat гостя жив; это не доказывает, что
  игра продвигается или компилирует шейдеры. Отчёт о выходе ВМ объясняет, почему не приложен отчёт
  macOS о сбое (не записан вовремя, нечитаем, неполон или относится к другому pid).
  Те же отсчёты один раз пишутся в лог при простое индикатора 10 с, в том числе при живом heartbeat:
  «Сообщить о проблеме» получает диагностику зависаний игры без включения статистики производительности.
  После паузы планирования на хосте (сам лаунчер несколько секунд не выполнялся) детектор сначала
  наблюдает новое окно heartbeat и не считает эту паузу зависанием гостевой системы.
- выход ВМ по SIGTERM/SIGINT/SIGHUP (выход из системы, `kill`, ^C до установки обработчиков) — не
  падение: только строка в логе, без события и без окна Сообщить о проблеме. SIGPIPE — тоже (оба
  процесса его игнорируют: закрытый канал вывода — терминал или канал stderr супервизора после того,
  как супервизор убит, — только даёт ошибку записи; процесс ВМ тогда пишет лог в
  `~/Library/Logs/es.fxgam.steamac/steamac-vm.log` или отбрасывает строки и даёт гостю довыключиться;
  STEAMAC-10). SIGKILL — событие
  `vm-killed` уровня warning «VM process killed (SIGKILL — memory pressure or force quit)»: убило ли
  ядро за память (jetsam, `NOTE_EXIT_DETAIL` из kqueue супервизора), память ВМ и footprint процесса ВМ
  при выходе/пик, `vm_stat`-числа хоста (free/compressed/wired, swap), `kern.memorystatus_level` и
  история уровней memory pressure с начала загрузки (переходы пишутся и в лог: `memory pressure: …`).
  Завершить принудительно из меню приложения (или повторный запрос выключения) — запрошенный выход, не
  отчёт: процесс ВМ выходит с кодом 3, и супервизор узнаёт это без файла-метки `user-exit` (при
  заполненном диске Mac метку не удавалось записать, STEAMAC-15);
  В `memory_history` — до двух минут отсчётов footprint ВМ и памяти хоста перед выходом (каждые 10 с);
  отдельный снимок при отчёте помечен как сделанный после выхода: память ВМ уже освобождена.
  Отчёты о потере GPU-контекста и SIGKILL добавляют недавнюю историю GPU/heartbeat процесса ВМ и
  снимки памяти процесса, Metal, выделений Vulkan и разделяемой памяти; эти счётчики перекрываются, их
  нельзя складывать. Вторая ВМ, отклонённая из-за занятого диска, выходит с кодом 4: объяснение, без отчёта.
- в каждом событии — последние ~200 строк stderr лаунчера как breadcrumbs (строки `[steamac-vm]`,
  `[mvk-*]`, предупреждения libkrun/virglrenderer, этапы загрузки) и теги: версия
  (`es.fxgam.steamac@<CFBundleShortVersionString>+<git sha>`), окружение и тег `build_kind`:
  `release` — только сборка `dist.sh` с нотаризацией (Info.plist `SteamacDistTeamID`, и подпись
  работающего кода — Developer ID этой команды, проверка `SecCodeCheckValidity`), `source-build` —
  любой другой `.app` (`bundle.sh`, ad-hoc/переподписанные копии, `dist.sh --no-notarize`),
  `development` — `work/out/steamac-vm` вне бандла; macOS, модель Mac, GPU, vCPU/RAM, режим дисплея,
  UUID сборок libkrun / virglrenderer / MoltenVK, `MVK_PATCH_REVISION`, версия ядра, BUILD_ID SteamOS
  и релиз слоя (из строк initramfs), `appid` игры в фокусе гостя (пока она в фокусе), случайный ID
  установки.

Не отправляется: консоль гостя (hvc0), имя пользователя и компьютера (`/Users/<имя>` → `~`, имя и
hostname вырезаются), IP (`sendDefaultPii=false`, сервер не выводит IP), локаль/часовой пояс,
аккаунт Steam, названия игр (только App ID), файлы. Супервизор пропускает свой stderr через канал
(всё по-прежнему попадает в терминал/лог), поэтому видит и последние строки упавшего процесса ВМ.

Проверка: `--sentry-test-event` (тестовое событие из супервизора и процесса ВМ, процесс ВМ заодно
отправляет отложенный отчёт о падении и выходит), `--sentry-test-crash abort|segv|metal|panic|kill|term|shader`
(процесс ВМ падает: `abort()` внутри вызова C, `EXC_BAD_ACCESS` в `memset`, assert Metal, паника
Rust в `krun_start_enter` из-за слишком длинной командной строки ядра — для `panic` нужны `--kernel`
и, при необходимости, `--initrd`; `kill`/`term` — процесс ВМ убивает себя SIGKILL (отчёт
`vm-killed`) или SIGTERM (без отчёта и окна); `shader` — печатает пример ошибки компиляции MoltenVK с
`[mvk-msl]` и строку vkr и выходит). Такие события идут с `environment=development` и тегом `test=true`.
`STEAMAC_SENTRY_DEBUG=1` печатает отладочный лог SDK (ответы сервера).

Символы: `build.sh` кладёт dSYM `steamac-vm` и библиотек бандла в `work/out/dSYMs` (libkrun,
virglrenderer и MoltenVK собраны без DWARF — там только таблицы символов). `dist.sh` загружает их и
каждый Mach-O приложения (исполняемый файл, Frameworks, помощники в Resources; каждый должен пройти
`sentry-cli debug-files check`) через `sentry-cli --url https://sentry.fxgam.es debug-files upload --wait` и
сохраняет dSYM в `work/out/dist/FX-Steam-Launcher-<версия>-dSYMs`. Нотаризованная сборка требует
`SENTRY_AUTH_TOKEN`, `SENTRY_ORG` и `SENTRY_PROJECT` (проверка до подписи; `--no-sentry-upload` отключает
загрузку): 1.9 вышла без загрузки, и падения в `steamac-vm` и libkrun остались без символов.

## Проверка обновлений

Релизы обновляются прямо в приложении (Sparkle); все остальные сборки проверяют последний релиз на GitHub
и предлагают DMG. Общие у них: окно рядом с окном ВМ (не поверх него, если на экране есть место; без
фокуса — клавиатура и захваченная мышь остаются у ВМ), пункт меню приложения **Проверить обновления…**
(«Доступно обновление: X.Y…» с отметкой Новое, когда версия найдена) и галочка **Проверять обновления
при запуске** в «Настройки → Основные» (сразу).

**Обновления в приложении (релизы).** Релиз (`dist.sh` кладёт в Info.plist фид и открытый ключ EdDSA)
использует [Sparkle](https://sparkle-project.org) 2.10.1 (`Contents/Frameworks/Sparkle.framework`, без
XPC-сервисов: приложение не в песочнице) с окном выше вместо своего интерфейса. Пока галочка включена,
он запрашивает `https://fxgl.github.io/steamac/appcast.xml` не чаще раза в 6 часов, в том числе во
время работы. Фид подписан целиком, у каждого обновления своя подпись EdDSA; обе проверяются ключом из
приложения до распаковки (`SURequireSignedFeed`, `SUVerifyUpdateBeforeExtraction`), кроме того Sparkle
требует совпадения подписи кода нового приложения. Версии, которым нужна более новая macOS (или другой
Mac), не предлагаются; проверка из меню объясняет почему. Новая версия показывает описание и кнопки
**Установить** (загрузка в фоне — SteamOS продолжает работать, **Скрыть** закрывает окно, **Отменить**
останавливает загрузку — затем установщик Sparkle её подготавливает), **Пропустить эту версию** и
**Напомнить позже**. Для подготовленного обновления: **Установить и перезапустить** — SteamOS
выключается ровно как по «Выключить SteamOS» (кнопка питания, до 180 с, никогда не принудительно), затем
установщик Sparkle заменяет приложение вне работающего процесса и снова его открывает; **Установить при
выходе** (и закрытие окна) — обновление установится, когда лаунчер завершится. Дельта-обновление (только
изменённые файлы) используется, если в фиде есть дельта от установленной версии, иначе — полный DMG.

Sparkle живёт в процессе ВМ (только он запускает NSApplication); выход никогда не идёт через AppKit
(гость выключается, и libkrun завершает процесс), а супервизор после перезагрузки гостя запускает новый
процесс ВМ из бандла — это гонка с установщиком, который его заменяет. Поэтому, пока обновление
подготовлено, процесс ВМ оставляет в run dir маркер `update`, и супервизор больше не загружает ВМ;
перезагрузка SteamOS (из SteamOS или «Перезапустить ВМ») превращается в «Установить и перезапустить».
Собственный запрос Sparkle на выход (он приходит после выключения, начатого лаунчером) игнорируется,
чтобы не стать принудительным выходом; второй выход пользователя по-прежнему принудительный.

Копии, которые не могут заменить сами себя, остаются с проверкой GitHub ниже (в логе `update: in-app
updates off (…)`): сборки из исходников (`bundle.sh`), dev-лаунчер, приложение, запущенное прямо из DMG
или транслоцированное Gatekeeper (не перенесённое в «Программы»), и копии на томе только для чтения.

Приватность: запросы Sparkle уходят только на `fxgl.github.io` (фид) и к загрузкам релизов GitHub, со
стандартным `User-Agent` (версии приложения и Sparkle); без профиля системы, идентификаторов Mac или
пользователя и Sentry. Своё состояние (время проверки, пропущенная версия) Sparkle хранит в настройках
приложения (ключи `SU…`).

**Проверка релизов GitHub (другие сборки).** При запуске приложения (один раз за запуск, не при каждой
перезагрузке ВМ, и не чаще раза в 6 часов — даже между запусками) лаунчер в фоне, не задерживая
загрузку, запрашивает последний релиз `https://api.github.com/repos/fxgl/steamac/releases/latest` (без
авторизации, таймаут 10 с; черновики и пре-релизы не учитываются) и сравнивает тег `vX.Y[.Z]` со своей
версией (`CFBundleShortVersionString`, численно: 1.3.10 > 1.3.9). Если вышла новая версия, окно
показывает «Доступен FX Steam Launcher X.Y — у вас версия …» с описанием релиза и кнопками **Загрузить**
(открывает в браузере `.dmg` релиза, иначе страницу релиза), **Пропустить эту версию** (эта версия
больше не предлагается при запуске) и **Напомнить позже** (снова — при следующей проверке). Пункт меню
проверяет сразу — без 6-часового ограничения и пропущенных версий — и сообщает «Установлена новейшая
версия» или ошибку; ошибки сети и HTTP при запуске только пишутся в лог (`update: …`). Dev-лаунчер
`work/out/steamac-vm` при запуске не проверяет (меню работает); сборки из исходников (`bundle.sh`) —
проверяют.

Приватность проверки GitHub: запрос уходит только на `api.github.com` (GitHub) и содержит только `User-Agent:
FXSteamLauncher/<версия>` (плюс стандартные заголовки HTTP и ETag прошлого ответа, чтобы GitHub мог
ответить «не изменилось»); никаких идентификаторов Mac или пользователя, cookies и Sentry. Время
проверки, ETag, ответ и пропущенная версия хранятся в настройках (`updateLastCheck`, `updateETag`,
`updateCachedBody`, `updateCachedURL`, `updateSkippedVersion`).

Тесты: `STEAMAC_UPDATE_URL` подменяет адрес (JSON релиза или массив `/releases`, `http(s)://` или
`file://`; заодно включает проверку при запуске dev-лаунчера), `STEAMAC_FAKE_VERSION` — версию
лаунчера, `STEAMAC_UPDATE_FEED` — фид обновлений в приложении; FIFO `--control-fifo`: `update
check|startup|state`, `update press download|skip|later|ok|releases|cancel|hide|install|quit`
(`install` / `quit`: «Установить и перезапустить» / «Установить при выходе»), `update dump PNG` (окно и
`-with-vm.png` — вместе с окном ВМ, как на экране). Локальный фид: см.
[Дистрибутив](#дистрибутив-dmg).

## Статистика игр

Какие игры запускаются и с какой скоростью работают на каком Mac: данные собираются у согласившихся
игроков и доступны всем на <https://fxgl.github.io/steamac/games.html> (`docs/games.html`).

Агент гостя следит за игровыми scope Steam (`app-steam-app<appid>-*.scope`, теми же cgroup,
которые замораживает **Поставить игру на паузу**) с каждым heartbeat раз в 1 с и сообщает
`game-start <appid>`, раз в 5 с — `game-mem <appid> <anon_kib> <guest_used_kib>` (анонимная
память игры и использованная память гостя), `game-proton <appid> <version>` (из
`compatdata/<appid>/version` в префиксе), сразу за ним `game-gfx <appid> dxmt|vulkan` (фактический
графический путь) и `game-exit <appid>`; `game <appid> <name>` следует
за первым `game-start` или получением фокуса данным app id за загрузку. Лаунчер (`GameStats.swift`)
создаёт один отчёт на запуск игры: сколько она работала и была в фокусе (не на паузе, ВМ не
приостановлена), появилось ли окно и через сколько времени (запуск без окна считается неудачным),
частота кадров по интервалам flush scanout-0 гостя, пока игра в фокусе (средняя, медиана,
1% low, задержки свыше 50 мс в минуту; промежутки свыше 1 с исключаются; `present_frame`
libkrun, те же flush, о которых сообщает `--perf-stats`), пиковая память игры / гостя,
пиковый `phys_footprint` процесса ВМ на Mac, разрешение, версия Proton и причина завершения
(`exit`, `shutdown`, `session`). Каждый отчёт содержит данные Mac (модель, чип, число
P-ядер и всех ядер, ядра GPU, ОЗУ, macOS), ВМ (vCPU, ОЗУ, Vulkan-драйвер, wmtr, частота
обновления, сборка SteamOS) и версию лаунчера.
Новые отчёты о сеансах и оценках используют схему `v:2` с необязательными `gfx` (`vulkan` или `dxmt`)
и `env` (разрешённые слова параметров запуска из «Профили отдельных игр», не более 256 символов).
Фактический путь берётся из `game-gfx`; оценка использует графический путь и слова последнего сеанса.
Сервис по-прежнему принимает v1 (включая ранее сохранённые сеансы), записывая `gfx`/`env` как NULL.
Неверные присваивания v2 отклоняются с HTTP 400; верные сортируются по имени, при повторе побеждает последнее.

Каждый отчёт хранится на этом Mac (`~/Library/Application Support/es.fxgam.steamac/game-stats.json`,
20 сеансов на игру) и показан в **Настройки → Игры**. Ничего не покидает Mac, пока не включено
**Делиться статистикой игр**: после первой игры с окном лаунчер спрашивает один раз, в окне рядом
с окном ВМ, не забирая клавиатуру или захваченную мышь (**Делиться** / **Не делиться**);
переключатель в «Настройки → Игры» позволяет изменить решение в любой момент. Пока он включён,
завершённые сеансы и оценки отправляются в сервис статистики (`POST /v1/sessions`,
`POST /v1/ratings`), включая сеансы, записанные ранее; игра с выключенной галочкой **Делиться**
ничего не отправляет, а её оценка отзывается (`"rating": "none"`). Загрузки идут по одной;
HTTP 400/413 приводит к удалению отчёта, при остальных ошибках попытка повторяется через
10 минут, при завершении следующего сеанса или следующей загрузке.

Приватность: без имени, имени пользователя или компьютера, аккаунта Steam, файлов или произвольного
введённого текста (передаются только разрешённые графические параметры запуска, описанные выше);
идентификатор установки — случайный UUID, используемый только для подсчёта разных Mac
и ограничения частоты запросов (не идентификатор отчётов о сбоях); сервис использует адрес клиента
только как временный ключ ограничения частоты запросов и никогда его не сохраняет.

Страница публикует только агрегированные данные, никогда — отдельные сеансы, и перечисляет чипы,
на которых проверена каждая игра. Конфигурации группируются по чипу, ОЗУ, Vulkan-драйверу,
графическому пути и словам параметров запуска (`gfx`/`env`; `wmtr` оставлен для совместимости).
У старых строк NULL `gfx` означает `vulkan` при `wmtr=0`, но неизвестный путь при `wmtr=1`:
само разрешение DXMT не доказывает, что игра его использовала.
Фильтр **Мой Mac** оставляет только отчёты с Mac не мощнее компьютера посетителя (число ядер GPU,
объём ОЗУ и число производительных ядер — каждое не больше указанного значения; в API —
`max_gpu_cores`, `max_ram_gb`, `max_pcores`): что работает там, должно работать и здесь.
**Открыть страницу статистики** в лаунчере передаёт параметры этого Mac
(`?chip=…&gpu=…&ram=…&pcores=…`) и включает фильтр; страница их запоминает.

`GET /v1/games/<appid>` также возвращает `recommended` (или `null`, если подходящего профиля нет).
Группы `(driver, gfx, env)` объединяют все чипы в пределах тех же фильтров «Мой Mac»; нужны минимум
две разные установки по совокупности сеансов и оценок, неизвестный графический путь не может победить.
Балл = `(well + 0.5 × issues) / все оценки` (ноль без оценок); при равенстве выше больший
`launch_rate`, затем меньший `early_exit_rate`, отсутствующие доли идут последними, далее —
детерминированный порядок драйвера/графики/env. Результат содержит драйвер, графический путь,
слова запуска, число установок/сеансов, оценки, медиану среднего FPS и долю успешных запусков.
Сайт и лаунчер показывают рекомендацию, но никогда не применяют её автоматически.

Сервис: `services/game-stats` — Cloudflare Worker с базой D1 (строгая валидация, идемпотентные
идентификаторы сеансов, 30 POST в минуту с одного адреса, суточный лимит на установку, агрегаты
`GET /v1/games` и `GET /v1/games/<appid>` кешируются на 5 минут в D1, потому что Cache API на
`workers.dev` ничего не делает). Развернуть один раз:

```sh
cd services/game-stats && npm install
npx wrangler login
npx wrangler d1 create steamac-game-stats      # put the printed database_id into wrangler.toml
npx wrangler d1 migrations apply steamac-game-stats --remote
npx wrangler deploy                            # prints https://steamac-game-stats.<account>.workers.dev
```
При обновлении существующего сервиса миграция `0002_profiles.sql` добавляет `gfx`/`env` в сеансы
и оценки и обновляет индексы группировки, сохраняя данные v1; `0003_responses.sql` добавляет
таблицу кеша ответов. Выполняйте `npx wrangler d1 migrations apply steamac-game-stats --remote`
**перед** `npx wrangler deploy`.

URL Worker указывается в `host/launcher/Info.plist` (`SteamacGameStatsURL`) и `docs/assets/games.js`
(`API`). Локально: `npx wrangler d1 migrations apply steamac-game-stats --local && npx wrangler dev`,
`npm test`.

Тесты: `STEAMAC_GAME_STATS_URL` подменяет адрес сервиса (и включает отправку в dev-лаунчере
`work/out/steamac-vm`, который иначе ничего не отправляет), `STEAMAC_GAME_STATS_FILE` — локальный
файл; FIFO `--control-fifo`: `guest game-start <appid>` и т. п. передают события трекеру,
`stats state|flush|ask|dump PNG|reset-question`, `stats press share|decline`, `settings games`.

## Сообщить о проблеме (Report a Problem)

Если что-то не работает, отправьте отчёт разработчикам прямо из лаунчера: **Справка → Сообщить о проблеме…**
(или в меню приложения), кнопка **Сообщить о проблеме…** в «Настройки → Основные», ссылка **Сообщить…** на
карточке «SteamOS не отвечает…» и кнопка **Сообщить…** в окне «FX Steam Launcher неожиданно
завершил работу», которое появляется после неожиданного завершения ВМ (падение, ошибка). В диалоге:
Электронная почта (обязательна, запоминается на этом Mac — чтобы разработчики могли ответить), описание (что
делали, чего ждали, что произошло) и галочки, что приложить:

- **Включить журналы приложения** (включено) — сообщения лаунчера, libkrun, virglrenderer и MoltenVK за эту
  сессию (последние ~2 МБ, оба процесса) и строки `perf:`/`stall:`; пути `/Users/<имя>` → `~`, имя
  пользователя и компьютера, email и IP вырезаются;
- **Включить журналы SteamOS (системный журнал, журналы Steam/Proton)** (включено) — консоль гостя (hvc0) за
  сессию и архив `steamos-logs.tar.gz`, который собирает гостевой агент: журнал systemd текущей загрузки
  (`journalctl -b`, последние 5000 строк, плюс пользовательский журнал), `coredumpctl list`/`info`,
  `dmesg`, `systemctl --failed`, `os-release`, `layer-release`, `/proc/cmdline`, `df`/`free`,
  ID/состояния/CPU/каналы ожидания потоков и имена команд (`threads.txt`, без аргументов), хвосты

  `webhelper`, `cef_log`, `shader_log`, `steamui_*`, логи Steam Input `controller`, `controller_ui` и
  `cloud_log`) и Proton (`~/steam-*.log` от `PROTON_LOG=1`, `version` и
  `config_info` префиксов в `compatdata`), build ID / манифест Steam / конфигурация FEX,
  параметры памяти, давление на память/ввод-вывод/CPU (`/proc/pressure/*`), `/proc/vmstat` и три
  отсчёта `vmstat`, хвосты логов SteamVR и стриминга (`vrserver`, `vrcompositor`, `vrmonitor`,

  Simulator. Для сбоя эмулятора ATS задайте параметры запуска в Steam

  и отправьте отчёт: в него войдут последние 512 КиБ лога. Затем уберите параметры запуска.
  Логи Proton больше 1 МиБ собираются после очистки: первый 1 МиБ начала работы и последний 1 МиБ,
  без середины, чтобы заголовок среды выполнения и первое исключение не терялись среди потока сообщений
  обработчика сбоев (STEAMAC-AA). В отчётах из режима рабочего стола отмечается, запущены ли `plasmashell`,
  KWin и Discover, и перечисляются флаги рендерера из разрешённого списка, без аргументов процессов
  и значений переменных окружения (STEAMAC-9P). В журналах лаунчера фиксируются соответствие требованиям
  Game Mode (ключи Info.plist во время работы и на диске), состояние нативного полноэкранного режима
  и отфильтрованные сообщения `gamepolicyd` (STEAMAC-9V).
  Если логов Proton нет, архив напоминает: чтобы увидеть сбой самой Windows-игры, нужны параметры
  запуска `PROTON_LOG=1 %command%`, одно повторение и новый отчёт. Логи Unity Player и текстовые логи
  Easy Anti-Cheat собираются из префикса Proton запущенной или последней запущенной игры и трёх недавно
  изменённых префиксов во всех библиотеках Steam (не более четырёх логов по 256 КиБ на префикс, без ссылок
  за пределы префикса, без сохранений и бинарников, с очисткой); это не означает, что игра или её античит
  работают.
  FEX перевыбрасывает сбой эмулируемой игры из своего JIT-кода, поэтому в стеке дампа виден только
  анонимный адрес AArch64. Чтобы узнать, где упал код x86_64, создайте
  `~/.local/share/Steam/steamapps/compatdata/<appid>/fex-emu/AppConfig/<исполняемый файл>.json` (ATS:
  `270880/fex-emu/AppConfig/amtrucks.json`) с содержимым
  `{"Config":{"Env":"LD_PRELOAD=/usr/lib/steamac/x86_64/fault-report.so"}}`, повторите сбой и отправьте
  отчёт. Параметры запуска Steam для этого не подходят: compat tool FEX убирает `LD_PRELOAD` из окружения.
  При SIGSEGV/SIGBUS/SIGILL/SIGFPE/SIGABRT библиотека записывает RIP x86_64, адрес сбоя,
  регистры, стек вызовов с модулем и смещением каждого кадра и карту памяти в
  `~/.local/state/steamac/fault-report.txt`. Файл не превышает 256 КиБ, в отчёт он попадает как
  `fex/fault-report.txt`. Затем срабатывает обработчик самой игры или действие по умолчанию: сбой и
  core-дамп не меняются. Без этого файла библиотека не загружается; потом удалите его. Root-хук
  экспортирует сведения о завершённых дампах только для `steamos` (владелец root, режим 0640);
  сами core-файлы остаются закрытыми и никогда не прикладываются. `coredump-pending.txt`
  перечисляет ещё обрабатываемые дампы: отчёт их не ждёт; после завершения отправьте новый.
  Разбор стека учитывает пространство имён pressure-vessel, если у библиотек есть символы
  (JIT-код FEX может остаться без символов). Лимиты обработки core не снижены: иначе большие
  дампы лишатся стека, а `Storage=none` всё равно пишет полный временный core. Steam ID
  (в том числе ID аккаунтов, как в `userdata/<n>`), имена аккаунтов/персон и email заменяются заглушками; `collect-notes.txt` перечисляет,
  что удалось прочитать. По SSH тот же очищенный архив доступен командой
  `/usr/lib/steamac/fx-progress-agent collect > /tmp/steamos-logs.tar.gz`;
- **Включить снимок экрана окна ВМ** (выключено по умолчанию: на картинке может быть имя
  аккаунта Steam и друзья).

Всегда прикладываются `system-info.txt` (версии приложения и macOS, модель Mac, GPU, UUID сборок
libkrun/virglrenderer/MoltenVK, ядро, BUILD_ID SteamOS, релиз слоя, размеры диска, параметры ВМ,
заметки о сборе) и `settings.txt` (сохранённые настройки и переопределения из командной строки;
пароль SSH лежит в связке ключей и никогда не попадает в отчёт, названия игр — тоже).
**Показать отправляемые данные** собирает отчёт и открывает его папку в Finder — отправляется ровно её
содержимое.

Отчёт уходит как User Feedback в Sentry (`sentry.fxgam.es`, тот же проект): email, описание, связь с
последним событием об ошибке этой сессии (если было) и файлы как вложения, одним конвертом напрямую
на envelope-endpoint — так виден ответ сервера. Работает и при выключенных отчётах о сбоях (явное
действие пользователя: SDK и обработчик падений при этом не запускаются). Вложения ограничены 20 МБ
(сначала обрезаются старые части логов, потом выбрасываются скриншот и архив SteamOS); на ответ
HTTP 413 лимит уменьшается вдвое и отчёт отправляется снова. После отправки показывается короткий
ID отчёта (первые 8 знаков ID события). Не удалось отправить — папка остаётся в
`~/Library/Logs/es.fxgam.steamac/reports/<дата>-<ID>/` (`report.json` с email и описанием плюс
файлы); в диалоге **Повторить попытку** и **Показать в Finder**, папку можно прислать почтой.

Как это устроено: супервизор всегда пропускает stderr обоих процессов через канал и пишет его в
`/tmp/steamac-<pid>/launcher.log` (с временем, ротация по 4 МБ), процесс ВМ пишет консоль hvc0 в
`console.log` рядом; каталог удаляется при выходе лаунчера. Гостевые логи запрашиваются по тому же
порту `fx.progress` в обратную сторону: лаунчер пишет `collect-logs <id>`, агент (от пользователя
сессии, только то, что тому доступно) отвечает `logs-begin <id> <размер>`, строками
`logs <id> <base64>` и `logs-end <id> <sha256>` (или `logs-failed <id> <причина>`), лаунчер собирает
архив и проверяет размер и SHA-256. Нет ответа за 20 с или агент не работает (нет heartbeat) —
отчёт уходит без гостевых логов, с пометкой в `system-info.txt`.

Проверка: `--control-fifo PATH`, команды `report open`, `report fill EMAIL ТЕКСТ…` (событие с тегом
`test=true`), `report include launcher|steamos|screenshot on|off`, `report preview`, `report send`,
`report retry`, `report dsn DSN|default`, `report dump PNG`, `report close`; `STEAMAC_REPORT_DSN`
подменяет DSN (путь отказа), `STEAMAC_SENTRY_DEBUG=1` печатает ответ сервера. Окно после падения:
`--sentry-test-crash abort` с `STEAMAC_REPORT_DUMP=<каталог>` (PNG окна и диалога, затем закрывается
само; `STEAMAC_REPORT_TEST_SEND=1` — заодно отправить тестовый отчёт).

### Курсор на пути DXMT

При wmtr DXMT выводит игру как `CAMetalLayer` внутри процесса ВМ на Mac. Слой расположен над
гостевым scanout и закрывает курсор гостевого композитора. В каждом новом гостевом агенте
отслеживание **выключено**. Лаунчер шлёт `cursor-track 1|0` по `fx.progress` при изменении
видимости/присоединения слоёв wmtr и повторяет текущее состояние при переподключении progress или
стартовом сообщении гостя `cursor-ready`. Повторное включение заново передаёт полный снимок курсора.
Для 1 нужны и фокус игры, допускающий игровые слои, и настоящий присоединённый, видимый
`CAMetalLayer` wmtr. Vulkan и Steam/рабочий стол без этого оверлея не требуют отслеживания курсора;
неизвестные команды хоста игнорируются для совместимости старых/новых хоста и гостя.

При включении гостевой агент (`guest/progress-agent/src/cursor.rs`) находит дисплей Xwayland,
у которого `WM_CLASS` активного окна начинается с `steam_app_`; обязательны поддержка XFixes и
активное окно игры, без подстановки корневого окна. Он получает начальную картинку через
`XFixesGetCursorImage`, затем обновляет её по событиям смены
курсора XFixes, а не периодическим опросом; `QueryPointer` опрашивает позицию не чаще 60 Гц,
только пока она нужна. Передаются лишь изменения: `cursor 0|1`,
`cursor-image <w> <h> <xhot> <yhot> <base64 BGRA>` и `cursor-pos <x> <y> <win_w> <win_h>`.
Позиция и размер — в пикселях клиентской области X-окна игры в фокусе, а не корневого X-окна:
у оконной игры корневое окно может быть больше клиентской области. Курсор 1×1 или полностью
прозрачный скрыт — Wine использует такие для игры без курсора.

Лаунчер разбирает сообщения в `Progress.swift` и через `Window.swift` передаёт их в `VMView`
из `Presenter.swift`, где есть прозрачный `CALayer` с именем `steamac.cursor-overlay` и
`zPosition` 1000. Он видим лишь при видимом игровом слое, видимом гостевом курсоре и известной
позиции; исключён из правил игровых слоёв и Metal HUD и присоединяется заново, если wmtr удаляет
подслои. Картинка становится `CGImage` с premultiplied-first. Перед отображением во view картинка
и hotspot масштабируются как при `--cursor-scale-height 720` в gamescope: при высоте окна игры H
желаемый размер — `clamp(36 * floor(H / 720), 36, 256)` пикселей. Как в gamescope, если хотя бы
одно измерение картинки больше желаемого, она уменьшается до квадрата, а координаты hotspot
усекаются до целых; иначе масштаб равномерный, не меньше 1, по отношению желаемого размера к
высоте картинки. Позиция в X-окне отображается в прямоугольник вывода активного удалённого
игрового слоя (`drawableSize`, вписанный с сохранением пропорций, как у wmtr), а не в картинку
гостя: отличие размера или пропорций игрового слоя от scanout гостя не сдвигает курсор.
Композитор выполняет окончательное масштабирование во view и альфа-смешивание.

Видимость следует **курсору самой игры**, а не скрытию gamescope после 3 секунд бездействия.
Правила курсора Mac не меняются: auto скрывает его над картинкой, захват — пока мышь захвачена;
в режиме tablet и при незахваченном `--mouse capture` могут быть видны и курсор Mac, и гостевой
оверлей. Захваченная мышь для обзора сама по себе не скрывает курсор, который игра считает видимым.

MoltenVK также исправляет fragment-хелперы с discard в иначе пустом блоке SPIR-V
(STEAMAC-1Q). `host/moltenvk/repro/msl_helpers.c` проверяет прямой и вложенный вызовы:
отброшенные пиксели остаются очищенными и не пишут в storage-буферы, остальные рисуются нормально.
Хелперы `log10(float)` переименовываются, чтобы не конфликтовать с перегрузкой Metal (STEAMAC-1R);
тот же repro читает результат compute-хелпера, а не только проверяет создание конвейера.

`vkCmdBindDescriptorSets` с `VK_NULL_HANDLE` среди наборов (допустимо с graphics pipeline
libraries) больше не роняет ВМ при отправке командного буфера (Counter-Strike 2 привязывает пять
наборов, четвёртый — null, STEAMAC-25): как в RADV, null-набор ничего не привязывает и не забирает
динамических смещений (`repro/invalid_usage.c`).

Выход фрагментного шейдера другого числового типа, чем его цветовое вложение (конвейер Left 4 Dead 2
из DXVK пишет беззнаковый выход в вложение `R32_SINT`, STEAMAC-2C; Vulkan оставляет значения
неопределёнными), не собирался в Metal, и draw с этим конвейером пропускались; теперь он объявляется
с типом вложения и записывает свои биты (`repro/frag_output.c`).

Вход вершинного шейдера без вершинного атрибута в конвейере (шейдер SCS Truck Simulator читает
`in_var_NORMAL` из location 1, который конвейер не описывает, STEAMAC-2Y; Vulkan оставляет значения
неопределёнными) не собирался в Metal («missing from the vertex descriptor»), и draw с этим конвейером
пропускались; теперь такие входы читают нули (`repro/vertex_input.c`).

Целочисленный вход вершинного шейдера с вещественным форматом атрибута (BLUE REFLECTION: Second Light
читает `BLENDINDICES1` как `int4` из атрибута `Float3`/`Float4`, STEAMAC-3N) не собирался в Metal
(«cannot be read using MTLAttributeFormatFloat3»), и персонажи были невидимы; теперь атрибут читается
в совместимом с форматом типе, а его биты переинтерпретируются (`repro/vertex_input.c`). Устойчивая
выборка через вспомогательную функцию с неизменяемым YCbCr-сэмплером больше не ломает компиляцию
(`is_null_texture`, STEAMAC-3W; `repro/texture_helpers.c`). Texel buffer view формата, для которого в
Metal нет пиксельного формата, возвращает `VK_ERROR_FORMAT_NOT_SUPPORTED` вместо падения процесса ВМ
(Uncharted, STEAMAC-3Q; `repro/texel_buffer.c`); texel buffer view шире 2^28 текселей Metal завершается
`VK_ERROR_OUT_OF_DEVICE_MEMORY` вместо аварийной остановки в проверке дескриптора Metal (STEAMAC-9E/79).
Несобравшийся графический конвейер пишет в лог точку
входа, хеш шейдера и интерфейс каждой стадии — для ошибок связывания и компилятора без MSL.

Корневая ФС SteamOS не модифицируется: все изменения приходят из initramfs и слоя. Поэтому
официальные обновления Valve (RAUC + atomupd) ставятся в другой слот и откатываются штатно —
проверено обновлением 20260922 → 20260928 и откатом.

Venus ICD слоя линкуются только с sonames, которые обновления SteamOS сохраняют
(`guest/mesa/container/verify.sh`, `check_stable_needed`); libdisplay-info не используется. SteamOS
0.6.0 (канал preview, 20261020) заменила `libdisplay-info.so.1` на `.so.3`: ICD из 1.9.7 не
загружался, gamescope не находил Vulkan-устройство и ВМ оставалась на «Starting Steam client»
(STEAMAC-72). Проверено обновлением stable → preview до 20261020 (0.6.0): Steam запускается в
обновлённом слоте.

## Статус

Проверено:

- загрузка SteamOS до `graphical.target`, автологин, gamescope-сессия; сеть (DHCP через gvproxy,
  скачивание обновления клиента Steam 583 МБ), SSH;
- Venus в госте: `Virtio-GPU Venus (Apple M4 Max)`, Vulkan 1.4; рендер-тест (compute + clear/copy)
  и вывод на экран через KMS совпадают с эталоном попиксельно;
- все обязательные возможности DXVK из Proton 11 / DXVK 3.x видны в госте (geometryShader,
  shaderCullDistance, depthClipEnable, robustness2 + nullDescriptor, maintenance5/6, …);
- клавиатура, планшет, мышь и виртуальный pad видны в SteamOS; как DualSense SDL в Steam сопоставляет
  его как `PS5 Controller` (тип PS5) и показывает значки PlayStation; pad появляется, исчезает и
  меняет вид, пока ВМ работает; вибрация из SDL и из виртуального pad Steam доходит до лаунчера
  (`rumble 49152 16384` 1,5 с, затем 0); воспроизведение на физическом контроллере ещё не проверено;
- проброс DualSense, сторона гостя: uhid-DualSense с настоящим USB-дескриптором отчётов, которого
  питает замена лаунчера, привязывает `hid-playstation` (геймпад, сенсорная панель, датчики движения,
  гнездо гарнитуры, RGB- и индикаторы игрока); касание и нажатие сенсорной панели доходят до её
  устройства, кнопка mute переключает индикатор mute выходным отчётом обратно на сторону Mac, а Steam
  открывает `/dev/hidraw*` своим HIDAPI-драйвером (`Controller using HIDAPI driver, vid=0x054c,
  pid=0x0ce6`). Сторона Mac (IOHIDManager, физический DualSense по USB или Bluetooth) ещё не проверена;
- режим рабочего стола: Switch to Desktop, рабочий стол Plasma с мышью (в том числе с полями), Return
  to Gaming Mode, загрузка сразу в рабочий стол; песочницы Flatpak запускаются;
- обновление A→B официальным OTA и откат;
- GL через zink (glamor в Xwayland, glxgears ~60 FPS), интерфейс Steam (gamepad UI, CEF с GPU)
  отрисовывается на экране ВМ;
- вход в Steam, установка Proton 11.0-2 (ARM64) и FEX, запуск DX11-игры (Death's Door) через
  DXVK → Venus → MoltenVK;
- разрешение гостя следует за размером окна при постоянном DPI; быстрое выключение (2–4 с);
- Heroes of Might and Magic: Olden Era (Unity, DX11) — 7 минут без ошибок (офлайн-проверка);
- American Truck Simulator (нативный Linux x86_64 под FEX, OpenGL 4.6 core через zink) — карьера
  загружается, мир отрисовывается на KosmicKrisp и на MoltenVK.

Подтормаживания при первом проходе — компиляция Metal (~50–100 мс на новый конвейер), повторно
~1 мс. При перезагрузке после аварийного выключения initramfs проверяет и чинит FAT на esp/efi.

## Ограничения

- DirectX 12 (vkd3d-proton): feature level 12_0 на KosmicKrisp (tiled resources tier 2: sparse-привязка и
  резидентность на placement sparse ресурсах Metal 4), 11_0 на MoltenVK; SM 6.0 на обоих (SM 6.2+ на Apple GPU нет:
  vkd3d-proton требует и обнуления денормализованных FP32-чисел, и их сохранения, а Metal их не сохраняет).
  virglrenderer пишет в журнал необходимые условия SM 6.0 и свойства денормализованных чисел для SM 6.2,
  которые сообщает каждое устройство. Age of Mythology: Retold останавливается с "Shader model too low (Shader_Model_60)"
  (STEAMAC-AB/AC/A0); на M5 Max с KosmicKrisp параметры запуска
  `VKD3D_DISABLE_EXTENSIONS= VKD3D_SHADER_MODEL=6_6 %command%` позволили пройти эту проверку и дойти до меню;
  это лишь переопределяет сообщаемую шейдерную модель, и в матчах игра всё ещё может завершаться.
  Внутри одного прохода рендера глубина, записанная в непривязанные плитки sparse depth-вложения, остаётся в тайловой
  памяти GPU Apple. Stellar Blade Demo (UE4) идёт в 1280×800, 60 FPS на M4 Max; первый запуск несколько минут
  компилирует шейдеры. x86-эмулятор Proton ARM64 (FEX) один раз уронил её через 20 минут (проверка DEP в защищённом .exe).
- Звук: virtio-snd → CoreAudio (устройство по умолчанию или выбранное в настройках), задержка ≈65 мс на встроенных
  динамиках. При загрузке воспроизведение получает до 12 PCM-каналов по раскладке динамиков устройства вывода,
  включая верхние (например, 5.1.2 или 7.1.4), если CoreAudio их явно определяет. Неклассифицированная/дискретная
  раскладка или устройство больше чем на 32 канала дают моно/стерео; 8 каналов сами по себе не означают 5.1.2,
  кодирования Dolby Atmos нет. Для многоканальной раскладки `audio-layout` до старта WirePlumber читает карту
  каналов VirtIO ALSA и заменяет стерео-политику SteamOS соответствующим выходом Pro Audio (таймерное
  планирование, раздельные группы воспроизведения и записи: у устройств хоста независимые часы); на стерео
  остаётся стандартный профиль SteamOS. Воспроизведение сразу переходит на новое устройство по умолчанию или
  при отключении выбранного, раскладку перепроверяет раз в секунду, раскладывает каналы по физическим динамикам
  и сводит недостающие с запасом по уровню. Карты каналов гостя фиксированы на загрузку (virtio-snd/ALSA их
  кешируют): чтобы игры увидели больше каналов или новую раскладку, перезапустите ВМ. `STEAMAC_SND_DUMP`
  пишет PCM гостя до раскладки по динамикам. 5.1.2 проверено на железе, 7.1.4 — только автотестами; микрофон
  остаётся моно/стерео и не проверен. Запись с микрофона идёт со входа macOS по умолчанию. Если доступ к
  микрофону запрещён, входного устройства нет или CoreAudio не запускается за 200 мс, запись завершается
  обычной ошибкой звука и не блокирует очередь управления звуком ВМ; воспроизведение от записи не зависит
  (STEAMAC-8N/8P: зависший старт записи оставлял буферы записи гостя невозвращёнными). В логе записи есть
  устройство ввода и состояние разрешения на микрофон.
- Античиты, которые блокируют ВМ, не пройдут.
- `logicOp` недоступен (приватный Metal API в форке MoltenVK не собирается); zink выдаёт предупреждение.
